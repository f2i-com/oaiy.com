# OAIY Relay Protocol v1

`oaiy-relay/1`: the wire contract between an OAIY relay (a small server the owner runs
themselves) and its clients: the OAIY desktop, a phone, a provider such as FormLogic, and
the Aokie plugin. The relay stores and forwards small opaque items in per-endpoint
mailboxes; clients fetch them with one multiplexed long poll of at most 20 seconds.

This folder is the contract, not an implementation. A relay written in any language is
conformant when it passes `../../tests/relay_conformance.py` (schemas and vectors) and,
later, the black-box suite that reuses those schemas against a running relay.

| File | What it is |
|---|---|
| `README.md` | this document: the normative rules |
| `*.schema.json` | JSON Schema 2020-12, ids `https://oaiy.com/schemas/relay/v1/<name>.schema.json` |
| `vectors.json` | known-answer vectors: inputs and expected outputs |
| `generate_vectors.py` | writes `vectors.json` (`--check` proves the file is current) |
| `verify_vectors.mjs` | an independent Node re-computation of every vector (`node:crypto` only) |
| `fixtures/` | recordings of the real relay for the code that reads it: sealed tokens, a whole pairing, the Aokie admission and frames (`fixtures/README.md`), each rechecked by an independent Python and Node reader |

Test: `python ../../tests/relay_conformance.py` (from `platform/protocol/relay/v1`, or from anywhere:
`python platform/protocol/tests/relay_conformance.py`).

Key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## The one idea

The relay is transport, not authority. Devices authenticate to it with revocable
capability tokens. What a desktop will actually do is decided by signatures it verifies
against keys pinned out of band, judged against the signer's clock, never the relay's. A
hostile relay can drop, delay and replay what is not sealed; it cannot forge a command,
a pairing or a chat request, and it cannot read sealed lanes. Every `from`, `subjectId`
and grant that the relay writes into an envelope is a hint, never an authority.

## Versioning

- `protocol` is `oaiy-relay/<major>`; the major is also the URL prefix (`/v1/`). A client that does not know the major MUST refuse with a plain message and MUST NOT guess.
- Within a major the relay MAY add optional fields, features and lanes. It MUST NOT remove or repurpose them, add required request members, or narrow a limit below what an older client can send without answering `426 upgrade_required`. Anything else is `/v2`, served beside `/v1` while both are needed. Consumers MUST ignore unknown members unless a schema says `additionalProperties: false`.
- A client uses a feature only if `info.features` lists it, and ignores features it does not know.
- `minClient` is compared with the optional request header `X-OAIY-Level` (default 1); a lower level gets `426`. In v1 `minClient` is 1.

## 1. Conventions

- **Base URL.** `https://host[/path]`. Every route below is relative to it and begins `/v1/`. https only; plain http is accepted by a client only for loopback in test builds. There is no `.local` http exception for relay credentials. **A relay with a plain-http base is outside the schemas by design** (Interpretation 61): the relay accepts `http://` for a loopback `public_url` only (`127.0.0.1`, `localhost`, `::1`), which is how its own tests and a developer's machine run, and every URL it then builds is `http://` or `ws://` (the admission's `gatewayUrl` and the three `relay` URLs), where `admission-plugin-response.schema.json` and `admission-mobile-response.schema.json` require `wss://` and `https://`. Such answers are not claimed to validate, the conformance suite does not ask them to, and a build that talks to one is a test build. A relay's `public_url` is path-free and MUST NOT share an origin with the provider or any other registered credential.
- **Encodings.** `b64u` is base64url without padding (RFC 4648 section 5). Padding, whitespace and characters outside the alphabet are refused. Where a value has a fixed decoded length, a reader also refuses a spelling whose unused low bits are not zero (see Interpretations). Timestamps are Unix seconds (integers). Sizes are bytes of the UTF-8 text as sent.
- **Raw bytes into hashes, MACs, signatures and key derivations.** A value that has a text spelling (b64u, hex, Crockford base32) enters SHA-256, HMAC, an Ed25519 signature or HKDF as its RAW bytes, never as its text: `pid` and `s` are 16 bytes, a nonce, a public key and a secret are the bytes their b64u text decodes to, a digest is its 32 bytes. `||` joins byte strings; a quoted string in an expression is its ASCII bytes and `0x00` is one zero byte. The only texts that are hashed, MACed or signed as text are those the description calls a text: an offer text, a canonical JSON text, a body text "exactly as posted" or "as sent", and the ASCII of a decimal time or of the twelve SAS characters. A JSON document that carries a b64u string carries the text of it, because a JSON string is text (the `pid` member of the approval receipt is the 22-character spelling). Interpretation 21.
- **JSON.** UTF-8 (RFC 8259). Request bodies are at most 1 MiB. Unknown members in requests and responses are ignored unless a schema says `additionalProperties: false`. Signed and MACed material is always verified over the exact bytes received and only then parsed; nothing is re-serialised before verification. Integer members are written as integers: a spelling with a fraction or exponent (`60.0`, `6e1`), and the spelling `-0`, is not an integer for the relay even though JSON Schema's `integer` accepts the first two and JSON's grammar the third (Interpretations 2 and 23).
- **Canonical JSON** is required in exactly one family, pairing, because the phone's format dictates it: keys sorted bytewise (by their UTF-8 bytes), no whitespace, integers only (a float, `-0`, or an integer outside -2^63 to 2^64-1, is refused, so that every integer has exactly one spelling), strings escaped as JSON (quote, backslash and control characters escaped; `/` and non-ASCII left as they are, control escapes `\b \f \n \r \t` or `\u00xx` in lower case). Keys are ASCII everywhere, so byte order and code point order agree. Signer-shipped texts (commands, results, tickets, rotation statements, enrolment bodies, admission claims, info) are NOT canonical: the signer chooses the bytes once and ships them.
- **Relay time.** Every response carries the header `X-OAIY-Time` (the relay's Unix seconds when the response is produced) and every dynamic JSON success body also carries `"time"`; `GET /v1/info` is static and carries the header only. A client keeps a relay offset `time - localNowAtReceipt`, sampled when the response is received (a held poll's time is its end, so a request-midpoint sample would be biased by half the hold), takes the median of the last five samples and slews the offset by at most 1 second a minute. Relay time is used for relay-side expiry, pairing windows, ring `expiresAt` on the phone, and for warning the owner of a clock difference above 60 seconds. It is NOT used to judge signed commands or tickets (section 9.4).
- **Headers.** Requests: `Authorization: Bearer <credential>`; optional `X-OAIY-Client: <product>/<version>` (diagnostics only, never used for authorisation); optional `X-OAIY-Level: <int>`. Responses: `X-OAIY-Relay: oaiy-relay/1`, `X-OAIY-Time`, `Cache-Control: no-store` (except ETag-validated GETs, which use `private, no-cache`, and the static `info`), `Retry-After` on 429 and 503, `X-OAIY-Hold: granted|refused` on held routes.
- **Methods.** GET, POST and OPTIONS are the methods first-party clients use. Every mutating route has a POST form (section 5); PUT, PATCH and DELETE are accepted as aliases for clients that prefer them. Anything else is `405 method_not_allowed`, including HEAD. The reason is deployment: stock web application firewall rules commonly allow only GET, HEAD, POST and OPTIONS, and a revoke must never be blocked by one.
- **Content types.** `application/json; charset=utf-8` both ways (the media type is compared case-insensitively and the charset parameter may be omitted). A request that carries a body with any other content type is `415 unsupported_media_type`. A request without a body needs no content type.

## 3. Mailboxes and items

A mailbox is an append-only queue with one consumer. Posts address `dev:<deviceId>` (a device
inbox; the id itself starts `dev-`, so an address reads `dev:dev-Q1w2E3r4T5y6U7i8O9p0aB`) or `rbx:<rid>` (a reply box).

**Delivered item** (`item.schema.json`, an element of `items` in a poll response):

```json
{"seq": 42, "id": "6b6e21fd-6cd2-41ed-ac1a-a30a91cbad3a", "lane": "cmd", "from": "prov-Q1w2E3r4T5y6U7i8O9p0aB",
 "at": 1790000000, "exp": 1790000060, "hdr": {"ct": "sealed1"}, "body": "<opaque string>", "rp": "Ry3kq0wEo2nq1c9h5c7Zab"}
```

| Field | Meaning |
|---|---|
| `seq` | unsigned integer below 2^53, per mailbox, allocated by the relay inside the post transaction from that mailbox's own counter, strictly increasing in commit order, first value 1, gaps allowed. It is not global, so a cursor reveals nothing about other mailboxes. |
| `id`, `lane` | as posted |
| `from` | the sender's device or provider id, `rbx:<rid>`, or `relay`. A hint for routing and logs. Never an authority. |
| `at`, `exp` | relay receive time and the relay-enforced expiry (`at + ttl`), relay time |
| `hdr` | small routing header, always an object, keys from the allow-list below only |
| `body` | an opaque UTF-8 string. The relay never parses, re-encodes or trims it. |
| `rp` | optional reply box id (lanes `ai`, `ai.in`) |

**Post form** (`post-request.schema.json`, an element of `items` in `POST /v1/items`):
`{"to": "...", "lane": "...", "id": "...", "ttl": 60, "hdr": {...}, "body": "..."}`. `to`, `lane`, `id`
and `body` are required; `hdr` is optional (absent means `{}`). `ttl` is an integer number of seconds from 1 to the lane's maximum (both published in `info.limits.lanes`); absent means the lane default; zero, negative, fractional, non-numeric, null or above the maximum is `400 invalid_item` (no silent clamping). It is a duration, not an absolute time, so a sender's clock cannot matter; the relay computes `exp`.

**`hdr` allow-list.** `re` (an item id: the item this answers), `ct` (one of `text`, `json`, `sealed1`, `tunnel1`, `noise1`), `eph` (for `tunnel1`: the browser's ephemeral public key in the tunnel's `ephPub` format, standard base64 with padding, 44 characters), `kid` (an id of at most 64 characters), `prio` (0 or 1), `n` (a non-negative integer), `sig` (b64u of an Ed25519 signature, at most 88 characters; used on `ring` items). Any other key is `400 invalid_item`. The serialised header (compact JSON with slashes and non-ASCII unescaped, as UTF-8) is at most 512 bytes; the largest header the allow-list can express is 405 bytes, so the cap is defence in depth, but a relay MUST still count it. `ct` values: `sealed1` is a signed container sealed with `crypto_box_seal` (section 10.3); `tunnel1` is the existing NaCl `crypto_box` envelope, standard base64 of `nonce(24) || box`; `noise1` is reserved. The relay does not require a particular `ct` on a lane; the receiver checks it.

**Item states.** `queued` (stored, never returned), `delivered` (returned by at least one poll), `acked` (a later poll passed `since >= seq`), `expired`. On ack or expiry the relay deletes the `body` immediately and keeps the metadata (`id`, lane, sender, times, state, SHA-256 of the body) for 10 minutes so that duplicates are recognised and the sender can ask for the state.

**Idempotency.** `(mailbox, lane, sender, id)` is unique while metadata is retained: an id belongs to the device that chose it, so another sender's item of the same id is a different item and neither sees the other's `seq` or conflicts with it. A repeat by the same sender with an identical body hash is answered `duplicate` with the original `seq`; a repeat by the same sender with a different body is `conflict`. Delivery to a consumer is at least once; consumers de-duplicate on `(from, id)`, the sender the relay names on the item and the `id`, and never on `id` alone (Interpretation 57).

**Epoch and reset.** The relay keeps a random 8 byte `epoch` (b64u, 11 characters), created at install and regenerated by a restore. Every poll response carries it; a client echoes the epoch it last saw. A poll whose `epoch` differs, or whose `since` is above the highest `seq` ever issued for the mailbox, is answered `reset: true` with the new epoch and the mailbox's highest `seq` as `cursor`, and no items. This catches a restored older backup even when new posts have already pushed a mailbox's counter past a client's saved cursor.

**Quotas.** Per inbox (`dev:` and `rbx:`): at most 512 live items and 8 MiB of live bodies. Of these, the bulk lanes (`ai`, `ai.in`, `ai.out`, `sync`) may hold at most 75 percent of the items and bytes (384 items, 6 MiB); at least 25 percent is reserved for `cmd`, `res`, `pair`, `ring` and `ctl`. Items the relay itself creates (`pair`, `ctl`) bypass the quotas. Per reply box: at most 2 `ai` items, 32 `ai.in` items and 2 MiB posted by the holder over its life. Per Aokie party mailbox: at most 1,024 live frames and 8 MiB, and no single sender may hold more than a quarter of either (256 frames, 2 MiB). Beyond a limit a post is `429 quota_exceeded` with `Retry-After: 5` (`429 relay_backpressure` on the compatibility routes). This is typed backpressure, never a silent drop.

## 4. Lanes, limits and who may post

`info.limits.lanes.<lane>` publishes `{"body": N, "ttl": {"default": D, "min": 1, "max": M}}`; the served `body` is the smaller of the configured cap and the largest body the calibration measured through the host's own stack. `body` counts bytes of the UTF-8 text. A relay MUST NOT widen a number past the maximum below; it may narrow one it can prove it must.

| Lane | Sender role to recipient | Max `body` | TTL default / max (s) | Body |
|---|---|---|---|---|
| `cmd` | `provider` (and, later, a `phone` holding the `cmd` flag) to `desktop` | 32,768 | 60 / 300 | `sealed1` container |
| `res` | `desktop` to the device that sent the `cmd` named in `hdr.re` | 98,304 | 300 / 3,600 | `sealed1` container |
| `ai` | reply box holder to `desktop` | 393,216 | 300 / 600 | `tunnel1` |
| `ai.in` | reply box holder to `desktop` | 65,536 | 300 / 600 | `tunnel1` |
| `ai.out` | `desktop` to the reply box | 393,216 | 360 / 900 | `tunnel1` |
| `pair` | the relay (on a phone's rendezvous response) to `desktop` | 16,384 | 900 / 900 | JSON text |
| `ring` | `desktop` to `phone`; call features | 4,096 | 30 / 300 | JSON text, signed in `hdr.sig` |
| `ctl` | `relay` or `desktop` to any device | 4,096 | 3,600 / 86,400 | JSON text |
| `sync` | `desktop` to `phone` | 65,536 | 21,600 / 86,400 | `json` or `sealed1` |
| `sig` | the Aokie plugin and phone, only through the compatibility routes; call features | 196,608 | 120 / 300 | `json` (later `noise1`) |

`flow`, `flow.in` and `flow.out` are reserved and not served in v1; a post naming them is `400 invalid_item`. A relay lists in `info.limits.lanes` every lane a client may post to through `POST /v1/items` that it serves (`cmd`, `res`, `ctl`, `sync`, and `ring` when call features are on); lanes reached only through reply boxes or the compatibility routes are listed when those routes are served.

**Who may post what** (enforced by the relay, `403 forbidden` otherwise):

1. `cmd`: a `provider` device to any `desktop` device of this relay. The relay does not track which provider is linked to which desktop: a personal relay has one owner, and what makes a desktop act is its own pinned provider keys, not the relay's table. A phone may post `cmd` only if the desktop set `canCmd` on that phone (default off).
2. `res`: only a `desktop`, only to the sender of the `cmd` whose id equals `hdr.re`, and only while the `cmd` metadata is retained (10 minutes after ack or expiry). A `res` without `hdr.re` is `400 invalid_item`.
3. `ai`, `ai.in`: only through `POST /v1/rbx/{rid}/items` with that reply box's secret; the recipient is the reply box's desktop. Through `POST /v1/items` they are `403 forbidden`.
4. `ai.out`: only the `desktop` named by the reply box.
5. `ring`, `sync`: only a `desktop` to a `phone` that this desktop approved (`ownerDesktop`). A `ring` MUST carry `hdr.sig`; the relay verifies it against the desktop's registered host identity key over `"oaiy/relay/1/ring" || 0x00 || body text exactly as posted` and answers `400 invalid_item` if it does not verify (the phone verifies again; the relay is not trusted). With call features off a `ring` is `403 feature_disabled`.
6. `ctl`: the relay itself, or a `desktop` to devices it approved.
7. `pair`: never by a client. The relay creates it.
8. A `provider` can never post to a `phone`, and a `phone` never to a `provider`.
9. `sig`: never through `POST /v1/items`; only through the compatibility routes.

**`ctl` messages** (`ctl.schema.json`; JSON text, at most 4,096 bytes, hints only; none grants authority and none is shown as trusted): `{"t":"provider.updated","id":"prov-..."}`, `{"t":"provider.rotated","b":"<b64u statement bytes>","s":"<b64u signature>"}`, `{"t":"device.revoked","id":"dev-..."}`, `{"t":"token.age","days":95}`, `{"t":"relay.notice","level":"info|warn","message":"<=200 chars"}`. A receiver ignores a `t` it does not know. A client renders `relay.notice` as plain text under the label "message from your relay (unverified)", with no links, no key-paste instruction and no formatting; a `ctl` message never starts an action by itself.

**`sync` items** carry a `sealed1` container with the domain `"oaiy/relay/1/sync"`, signed by the desktop host identity and sealed to the phone's X25519 key. The relay never looks inside.

**What does not belong in a mailbox:** media, push origination (the optional FCM sender is a separate add-on), bulk data, code, records and app data, anything that must survive more than 24 hours.

### 5.1 `GET /v1/poll?since=&epoch=&wait=&limit=&maxBytes=&re=&peek=`

| Parameter | Default | Rule |
|---|---|---|
| `since` | 0 | cumulative, batched acknowledgement: one integer per poll acknowledges every item in this inbox with `seq <= since` and deletes its body; there is no per-item ack call. A negative, fractional or non-integer value is `400 invalid_request` |
| `epoch` | none | the epoch the client last saw; a mismatch is `reset: true` |
| `wait` | 0 | seconds the server may hold the request, at most `info.wait.max` (a larger value is clamped) |
| `limit` | 32 | 1 to 64 items; outside that range is `400 invalid_request` |
| `maxBytes` | 1,048,576 | 65,536 to 1,048,576; the first item is always returned even if larger; outside that range is `400 invalid_request` |
| `re` | none | return only items whose `hdr.re` equals this id; the request is a lookup; the response `cursor` equals `since` |
| `peek` | 0 | 1 returns items without acknowledging them or marking them delivered; the request is a lookup |

Response `200` (`poll-response.schema.json`): `{"v":1,"epoch":"<b64u>","cursor":42,"items":[...],"more":false,"time":1790000000,"hold":{"granted":true}}`. Items are in ascending `seq` and are only those with `exp > now` and not acknowledged. `more` is true when further items exist beyond `limit` or `maxBytes`; the client polls again at once. An empty result after a full wait is `200` with `items: []`. `cursor` is advisory: a client persists the highest `seq` of the items it accepted and ignores `cursor` on any non-empty response; only on `reset: true` does it adopt the server's `cursor` (which may be lower), once, and record "mailbox reset: in-flight items may be lost". A hostile `cursor` in a 200 with items therefore cannot move a client's position.

Four rules apply to consumer polls (a poll with neither `re` nor `peek`):

- **Gap.** A consumer poll whose `since` is not greater than the previous poll's `since` and which starts less than `info.wait.pollGapMs` (250) after the previous consumer poll of this device ended gets `429 rate_limited`, `Retry-After: 1`, `error.rule: "gap"`. A poll that follows a non-empty answer, or whose `since` advanced, is never refused by this rule (so a burst of three items posted together is three successful polls, not a 429 and a one second sleep), and neither is the poll that follows a `reset: true` answer: the relay records no end of a poll for it.
- **Supersede.** A consumer poll from a device that already holds one ends the older within 250 ms (the relay's step is 200 ms, section 5.1.1) with `items: []` and `hold.superseded: true`; it stops a client that timed out and retried from leaving a zombie held request behind.
- **In flight.** At most three consumer polls that wait (`wait > 0`) of one credential run at once, the one a newer poll is superseding included (each holds a worker until it notices, up to a step). A fourth is refused `429 rate_limited`, `Retry-After: 1`, `error.rule: "in_flight"`, before the poll reads or writes anything of its own (the check of the credential, which comes first, is the one database read a refused poll costs: Interpretation 58). Polls that arrive in the same instant can be refused beyond the surplus: each takes its place first (a marker) and counts the others second, and when several do that together each may count the others, so the relay can refuse more than the polls above three (the review measured a burst of four refusing two and a burst of five refusing four, and a burst of eight can refuse all eight) while it never lets more than three run; a client does not rely on one of a burst being let through, and follows P4 for every refusal. **A client MUST NOT treat this `429` as a failure, and MUST honour `Retry-After` (an upper bound of 120 seconds, with up to 20 percent jitter, section 7.1), before it polls again;** section 5.1.1 says exactly how, for this refusal and the gap rule's, which `error.rule` tells apart. An honest client has one poll in flight, two for the moment between a retry and the end of the poll it replaces, and never meets the rule; a client that opens many at once, or that cancels a poll and opens another faster than the older ends, does. The native pollers (the desktop relay client, DK-03, and the phone's, MOB-21a) are required to implement section 5.1.1; the shipped Aokie carriers ignore `Retry-After` on their stream routes and count a `429` there as a failed attempt (Interpretation 53), which is why the stream routes have a bucket sized for them and polls do not need one.
- **Hold accounting.** The poll is counted in the hold registry (section 7.2) and may be answered as a `wait=0` poll with `hold.refused: true` and `retryAfter` when the pool is nearly full.

**Lookups.** A poll that carries `re` or `peek=1` is a lookup: a read of what is already in an inbox by a party that is not consuming it. A lookup never acknowledges (its `since` is only a lower bound), never marks an item delivered, is exempt from the gap rule, never supersedes and is never superseded, does not write presence, and counts against the `tok.req` bucket. A lookup with `wait=0` is allowed for any role on its own inbox. A lookup with `wait > 0` is allowed only for role `provider`, is clamped to `info.limits.lookupWait` (8 s), and one device may hold at most `info.limits.lookupHeld` (4) waiting lookups at once (a fifth is `429 rate_limited`, `Retry-After: 1`); a phone or a desktop asking for one is `403 forbidden`. A waiting lookup wakes on any post to that mailbox and answers only when an item with the requested `hdr.re` exists, otherwise `items: []` at its deadline.

### 5.1.1 The poll loop of a native client (DK-03 and MOB-21a)

DK-03 is the work package that builds the desktop's relay client (enrolment by a pasted key, the poll loop, persistence and the status the user sees; package DK-03 of the relay design) and MOB-21a the one that builds the phone's (the Android app's relay client: poll loop, post, admission and the relay-time offset; package MOB-21a of the mobile design). Neither exists yet, and nothing in this repository polls as a native client does, so these rules are what both are built to and what their tests check: `fixtures/poll-client/poll-client.json` is a table of answers and the pause and state each must lead to, read independently by `verify_poll_client.py` and `verify_poll_client.mjs` (both run by `protocol/tests/relay_conformance.py`, which also pins the number of its cases and the digest of their names, so that a case that goes missing is noticed), and a client's own test loads the same table. In these rules a **poll** is a consumer poll that waits (`wait > 0`, no `re`, no `peek`); **the credential** is the device (the relay counts per device id: every bearer one device holds counts together, and two processes that poll with one device's credentials share the bound); a pause is in seconds unless it says `ms`. The relay's **step** is 200 ms: it looks for a newer poll of the device, a revocation and new items every 200 ms, so that a poll that a newer one supersedes ends within a step and the time of a request, which this protocol rounds up to 250 ms wherever it states a bound (section 5.1, Supersede, and P1).

**P1. One poll at a time, and how long a poll may take.** A client has at most one poll in flight for a device. It may cancel a running poll and start another (a changed network, a new `since`), but starts the new one no sooner than 250 ms after it started the one it cancels: the relay ends a superseded poll within 250 ms and counts it until it has, so a client that keeps to this has at most two of its polls alive and never meets the bound of three. A poll's own timeout is `wait + 10` seconds (10 for a poll without a `wait`): a poll that reaches it is **no response** under P2 and is paced by P5 like any other failure; it is not a replacement under P1, which is for a poll the client cancels on purpose. The client sends `wait` itself: `info.wait.default` for a poll that is to be held (20 unless the relay says less); a poll without `wait` is a short poll (`wait = 0`), which the relay answers at once, never counts in flight, and judges by the gap rule like any other.

**P2. Every answer is exactly one of six outcomes**, and nothing else decides what the loop does next:

| Outcome | What the client got | Counters |
|---|---|---|
| **progress** | a valid `200` (below) with at least one accepted item (below), or with `reset: true` | all four cleared |
| **superseded** | `200` with `hold.superseded: true`: a newer poll of the device replaced this one. A client that replaced it itself discards the answer and starts nothing (the newer poll is its loop); a client that did not has another process polling with its credential, reports that (`duplicate_credential`), and pauses as after an idle answer (P3) before it polls again | all four cleared |
| **idle** | any other valid `200` (`items: []` after the wait ran out, an answer none of whose items was accepted, or a refused hold, `hold.refused`). A `200` is **valid** when its body is a JSON object whose `items` is an array, whose `epoch` is a string of 11 characters of the base64url alphabet (8 bytes) and whose `cursor` is an integer from 0 to 2^53 - 1: `poll-response.schema.json` requires all three in every `200` | all four cleared (the count of refused holds rises when the answer is a refused hold) |
| **flow** | `429` with any code, any rule, any body | the 429 count rises by one; the failure count, the count of refused holds and the 400 count are cleared |
| **failure** | no HTTP response (refused, reset, TLS error, timeout of P1, a body that ends early or is not JSON), `408`, `500`, `502`, `503`, `504`, any other `5xx`, any `1xx`, `3xx` or `2xx` other than a valid `200` (a redirect is never followed: the relay does not redirect), a `200` that is not valid (a reset that carries no usable `epoch` or `cursor` is one: nothing is adopted, and the stored `since` and `epoch` stay as they were), the first `400` of a run, a valid `200` whose accepted items (or whose reset) could not be written to the client's store (see to persist, below), and a `426` that does not make the client too old | the failure count rises by one; the other counts are cleared (a `400` raises the 400 count) |
| **stop** | any other `4xx`, a second `400` in a row, and a `426` that does (the paragraph below) | the loop ends; the counters are left as they were, to be reported with the stop |

The rows are tried in the order of the table and the first that fits is the answer: a refused hold, or a superseded answer, that carries an accepted item is progress, not idle (the items are accepted, and the next poll acknowledges them). **An integer** in a poll answer (`cursor`, `seq`, `retryAfter` and `hold.retryAfter`) is an integer literal: digits only, with an optional minus sign, with no fraction, no exponent and no `-0`. `1.0`, `5.0`, `1e2` and `-0` are numbers to JSON and are not integers here: the relay never writes one, and a client that reads them as integers (a JSON parser that returns 1 for `1.0` does) accepts an answer that the schema's integers do not. A `cursor` that is not one makes the `200` not valid, a `seq` that is not one is not accepted, and a `retryAfter` or `hold.retryAfter` that is not one is read as absent; a `seq` above 2^53 - 1 is not accepted either. A client therefore reads the text of the answer, not only what its parser makes of it (a parser that gives the source text of a number, or one that reads numbers lexically, does). A **success** is progress, superseded or idle: the relay answered the question. A **429 is never a failure**: it does not change the connection state the user sees (still connected), does not count against any budget, and does not make the client re-enrol, reconnect, open another connection or drop its cursor. A stop is never retried by the loop, and each leads to one **action**: `401 revoked` means the device was revoked, `forget_credential`; any other `401` means the credential is not accepted, so `refresh_or_reenrol` (the client refreshes it once if it can, otherwise it ends the loop and asks the user to enrol again); `426` makes the client re-read `GET /v1/info` (section 8.5) and, when `info.minClient` is above its own level, end the loop and tell the user to update, `update_client` (when it is not, the `426` is a failure); every other `4xx` (`403` including `feature_disabled`, `404`, `405`, `413`, `415`, `422`) is a defect in the client or a relay that is switched off, and ends the loop with the code reported, `report_defect`. **A `400 invalid_request`** can only come from what the client built: `since` and `epoch` are what it persisted (the `epoch` is sent back byte for byte as the relay gave it), `wait`, `limit` and `maxBytes` are constants of its own; so it is a defect or a damaged store. The first `400` after any other answer is a failure that reports `invalid_request` and whose retry leaves out the stored `epoch` (action `clear_epoch`: an omitted `epoch` is no check, the answer carries the relay's current epoch, which the client stores, and a later mismatch is an ordinary reset); a second `400` in a row is a stop, `report_defect`. **An item is accepted** when its `seq` is an integer above the `since` the poll carried and above the `seq` of the item accepted before it in the same answer: the relay sends items in ascending order and never one that was acknowledged, so an item that is not is the relay's defect or a replay, and is dropped (not acted on, and not acknowledged by the next poll's `since`). `since` becomes the highest `seq` accepted, or, on a reset, the `cursor` of the answer; an answer none of whose items is accepted is idle. **A `reset: true` answer** is progress with nothing to acknowledge: the client adopts the cursor and the epoch of the answer once (the cursor may be lower than the `since` it had: that is what a reset is) and records "mailbox reset: in-flight items may be lost" (section 5.1); the relay records no end of a poll for it, so the gap rule never refuses the poll that follows, which carries the adopted `since` at once. **To persist** is to write what the client accepted (the items, or what it needs of them to act on them once, and the highest `seq` among them, with the `epoch`) to its durable store and have the write succeed before it sends the poll that carries that `seq` as `since`: that poll is the acknowledgement, and the relay deletes the bodies it acknowledges. If the write fails (the items, or the adoption of a reset) the client does not advance `since` (the items come again, and a consumer that de-duplicates on `(from, id)`, Interpretation 57, drops the repeats), and the answer is a **failure** for the pause: the failure count rises and the pause is P5's, so that a store that keeps failing is polled at the capped pauses and not in a tight loop (the gap rule would answer a tight loop with `429`s, which a client does not rely on); it reports `storage_failure`, and never `unreachable` (the relay answered: as for the first `400`, P7); `since` never goes beyond what is stored.

**P3. The pause after a success.** After **progress** there is no pause: the next poll carries the advanced `since` and the gap rule never refuses it. After **idle** the client waits `info.wait.pollGapMs` (250 by default, 0 to 5000; at most 300 seconds old, P9) before it polls again with the same `since`, because a poll that makes no progress sooner than that after the last one ended is the gap rule's `429`. After a refused hold the client does what section 7.2 says (it short-polls with `wait = 0`, asks for a hold again on every request, and counts the answer as idle): the pause is `max(r, min(F, r * 2^k))`, with `r` the `hold.retryAfter` of the answer (2 when it is absent or not an integer, then clamped as in P6), `F` the `info.wait.fallbackS` (5) and `k` the refused holds in a row before this one: 2, 4, 5, 5... seconds. After **superseded** it waits for nothing when this client replaced the poll itself (the newer poll is the one running), and as after idle (`info.wait.pollGapMs`) when it did not.

**P4. The two refusals of a poll are told apart by `error.rule`.** A `429 rate_limited` of a consumer poll carries `"rule":"gap"` (a tight loop that makes no progress: section 5.1, Gap) or `"rule":"in_flight"` (more polls of the device running than the bound: section 5.1, In flight) in its `error` object, beside `code`, `message` and `retryAfter`; any other `429` (a bucket of section 7.1, a proxy) has no `rule`, and a client that meets a `rule` it does not know treats it as none. Both are handled the same way, as **flow**: the pause of P5, then the same poll with the same `since`. What differs is what the client learns: `gap` says the pause of P3 was not kept, and `in_flight` says the client has, or shares its credential with, more polls than P1 allows; on `in_flight` the client also cancels every poll of its own that is still in flight (the action `cancel_own_polls`, on every `429` that says `in_flight`): the relay counts a cancelled poll until it ends, within 250 ms (P1), and the pause of P5 is at least one second, so the next poll starts after the relay has stopped counting them. The fifth `429` in a row, when it says `rule: "in_flight"`, is a defect to report once (`in_flight_defect`, P7); the loop goes on.

**P5. How long to pause after a `429` or a failure.** With `D` the `Retry-After` of the answer as P6 reads it (when there is none: 1 for a `429`, nothing for a failure) and `n` the count of the outcome in a row after this answer (the first `429` is `n = 1`):

- **flow:** `base = max(clamp(D), min(30, 2^(n-1)))`: 1, 2, 4, 8, 16, 30, 30... seconds, or the relay's own figure when that is longer.
- **failure:** `base = min(60, 2^(n-1))`: 1, 2, 4, 8, 16, 32, 60, 60... seconds, and `max(base, clamp(D))` when the answer had a `Retry-After`, except for the first `400` and for a failed write (P2), which are paced by the backoff alone: the first is the client's own request being wrong, and neither is the relay's load telling the client to wait.

**P6. `Retry-After`, the clamp and the jitter.** The relay sends the header as a count of whole seconds and repeats it as `error.retryAfter` in the body of a native error. A client reads the header first: after trimming spaces and tabs, one to six decimal digits are that many seconds; an HTTP-date (the IMF-fixdate of RFC 9110, `Sun, 06 Nov 1994 08:49:37 GMT`, that is a real date and time: the day within its month, hour 00 to 23, minute 00 to 59, second 00 to 60, year 0001 to 9999; the name of the day is not checked) is the seconds from the `Date` header of the same answer (from the client's own clock when that header is absent or unreadable) to it, and a date that has passed is 0; anything else (empty, a sign, a fraction, text, seven digits, a date that does not exist such as hour 25, day 32 or year 0000) is no header. With no readable header it reads `error.retryAfter` when that is an integer from 0 to 86400, and otherwise there is no `D`. `clamp(x)` is `x` limited to 1 to 120, so that 0 is 1 (a client never spins) and 600 is 120 (section 7.1). Every pause the rules name (P3's after idle, P5's) then has jitter added: `pause = base * (1 + 0.2 * u)` with `u` drawn for that pause, uniform from 0 up to but not including 1, never a constant.

**P7. What the client reports, and the budget.** There is no budget that ends the loop: a poll loop runs for as long as its credential lives, at the capped pauses above, and a `429` or a failure never ends it. What is counted is what the user is told: after three failures in a row (about seven seconds) the client reports the relay as unreachable (`unreachable`), and any success or a `429` (it proves the relay answered) clears that. A failure that is the client's own, and not the relay's, raises the count that paces the retries but never carries `unreachable`: the first `400` (the relay answered, and what is wrong is the request the client built: it reports `invalid_request`, P2) and a storage failure (`storage_failure`, P2); a failure after them that is neither reports `unreachable` when the count has reached three, which includes theirs; when the fifth `429` in a row says `rule: "in_flight"` it reports a defect of its own (`in_flight_defect`), once, and goes on. The reports a decision can carry are exactly these: `unreachable`, `in_flight_defect`, `duplicate_credential` (P2), `invalid_request` (the first `400`, P2), `storage_failure` (P2); the actions of a stop, a retry or a refusal are exactly `forget_credential`, `refresh_or_reenrol`, `update_client`, `report_defect`, `clear_epoch`, `cancel_own_polls` (P4) and (P9) `report_relay_changed`.

**P8. State.** A client keeps four numbers and two times for these rules, and nothing else: the 429 count, the failure count, the count of refused holds in a row and the 400 count (the counters of P2's last column), the time it started its last poll (P1) and the time its last proof of the relay succeeded (P9). They are cleared as P2 says, are not kept across a restart of the client (a restart proves the relay first, P9), and are left as they were by a stop (they are reported with it) until the client is enrolled again.

**P9. The relay's identity, and `info`.** A poll carries the device's bearer, so the client first has the proof of section 8.3: before the first poll of a process, after any pause of 60 seconds or more (the capped failure pause, a long `Retry-After`), after a change of network, and at least every 300 seconds while it polls, it asks `GET /v1/info` with `X-OAIY-Nonce` and verifies the answer against the key it pinned (section 8.2). The same answer is the `info` the loop uses (`info.wait.default`, `pollGapMs`, `fallbackS`, `minClient`), so a value in use is at most 300 seconds old; an `info` read without a nonce is cached for ten minutes (section 8.5) and is never what the identity rests on. While the proof has not succeeded the client sends no poll and no token. A proof that verifies is the outcome `proved`: no pause, the time of the proof is set, and the failure count is cleared (it proves the relay answered, as P7 says of a success), while the 429 count, the count of refused holds and the 400 count stay as they were: a proof is not an answer to a poll. No answer to the proof request is a failure like any other (P2 and P5: the failure count rises, the other counts are cleared); an answer that does not verify (a replayed body and signature, another key) is a stop, `report_relay_changed`: the client reports the relay as "not who it was", keeps its credential and does not send it, and the counters are left as they were (a stop, P2).

**What the shipped carriers do, for comparison, and why none of this is a copy of them.** The Aokie plugin and the Aokie phone app (the compatibility routes, section 10.6; they do not call `GET /v1/poll`) read no `Retry-After` at all, wait a fixed second before they open a stream again (plugin `companion_relay.rs` 50-52 and 670-677; phone 70-72 and 458-460), absorb three failures in a row and end the session on the fourth (plugin 53-56 and 745-755; phone 73-76 and 560-564), and count a `429` on a stream open as one of them, so that for them a `429` is a failure, which is why the stream routes have a bucket sized for these constants (Interpretation 53) and why the rules above are written for a client that is not one of them. A frames post is retried three times 250 ms apart by both (plugin 59-61; phone 647-700), and a `429` after the third is dropped by the plugin (`post_frames`, 980-1031) and reported by the phone (663-691).

### 5.2 `POST /v1/items`

Body `{"items":[{"to","lane","id","ttl","hdr","body"}, ...]}`, 1 to 64 items, at most 1 MiB. Response `200` (`post-response.schema.json`): `{"v":1,"results":[{"id":"...","status":"queued","seq":43},{"id":"...","status":"rejected","error":{"code":"quota_exceeded","message":"..."}}],"time":N}` with `status` one of `queued`, `duplicate` (carries the original `seq`), `rejected` (carries `error`). Errors that concern the request as a whole (`400`, `401`, `413` for a body over 1 MiB, `429`) use the normal error shape. Partial success is normal; a sender retries only the rejected items whose code is retryable (section 6).

### 5.3 `GET /v1/items/{id}?to=dev:<deviceId>&lane=<lane>`

Only for an item this device sent. `to` and `lane` are both required because an id is unique only per mailbox and lane. `200` (`item-state.schema.json`): `{"id","lane","to","state":"queued|delivered|acked|expired","seq","at","exp","deliveredAt":N,"ackedAt":N,"time"}`; `deliveredAt` and `ackedAt` are omitted until they happen. `404` otherwise.

### 5.4 Slots, presence, devices

**Slots.** `POST /v1/slots/{name}` with `{"body":"<at most 65,536 bytes>","ttl":120,"ct":"json","readers":["phone:caller_read","provider"]}`; `name` matches `[a-z0-9][a-z0-9._-]{0,63}`; TTL 1 to 3,600, default 120; only a `desktop` writes. `readers` is a list of at most 8 entries from `provider`, `desktop`, `phone` (any approved phone of this desktop) and `phone:<grant>` (an approved phone whose device row holds that grant); absent or empty means only the writer, and a name starting `private.` is writer-only whatever `readers` says. Response `200` (`slot-response.schema.json`) `{"etag":"\"<b64u>\"","exp":N,"time":N}` where the ETag is `"` + b64u(first 16 bytes of SHA-256(`body || 0x00 || ct`)) + `"`, `body` being the UTF-8 bytes of the body text exactly as posted (never decoded, whatever it holds) and `ct` the ASCII of the content type. `If-Match` gives compare-and-set (`412 precondition_failed`). `GET /v1/slots/{deviceId}/{name}` returns `slot.schema.json` with the same `ETag` header; `If-None-Match` gives `304`; an absent or expired slot is `404`; a caller who is not a listed reader is `403`; a revoked device is `401` at once. The reader list is set by the writer, which is the desktop, which is the authority for who may see what.

**Presence.** `GET /v1/presence` returns `presence.schema.json`. `online` means a consumer poll (not a lookup) is held now or started within `max(info.presenceWindow, info.wait.max + 5)` seconds. The ETag is a weak validator over the `devices` array only. A provider sees only desktops; a phone sees its desktop; a desktop sees all.

**Devices.** `POST /v1/devices/self/meta` (`device-meta-request.schema.json`) `{"name":"<=60","ver":"<=32","caps":["<=64 chars", at most 32],"ed25519":"b64u","x25519":"b64u"}` answers `ack.schema.json`; keys are recorded with a `keysChangedAt`. `GET /v1/devices` (desktop only, `devices-list.schema.json`, entries `device.schema.json`) lists the caller's own phones and providers. `POST /v1/devices/{id}` (desktop only; `device-patch-request.schema.json`, answer `device-patch-response.schema.json`) accepts `{"name"?, "flags"?, "grants"?}`; grants are patchable, so a takeover tier does not need a re-pair, and the next admission carries the new scopes. `POST /v1/devices/{id}/revoke` (desktop only; only that desktop's phones and any provider, never a desktop) answers `204` and, immediately and completely: revokes the device, revokes its tokens, purges its inbox and pending items, its party mailboxes, its slot access and its push registration, and any hold it has ends with `401 revoked` within 250 ms. `POST /v1/devices/revoke` `{"role":"phone"}` (`devices-revoke-request`, `devices-revoke-response`) does that for every phone of this desktop.

**Tokens.** `POST /v1/tokens/rotate` answers `200` `{"token":"oaiyrt1....","graceUntil":N,"time":N}` (`token-rotate-response`); the old token keeps working until `graceUntil` (now + 600). A second rotation during the grace is `409 conflict`.

**Keys and providers.** `POST /v1/keys` (desktop): `{"role":"provider","ttl":3600,"name":"FormLogic"}` gives `201 {"uri":"oaiy://enroll?...","kid":"...","exp":N,"time":N}` (`keys-request`, `keys-response`); the first desktop key comes from the installer or the admin CLI, never from the network. `POST /v1/providers` (provider token; `providers-request`): `{"name":"FormLogic","ed25519":"b64u","x25519":"b64u","origins":["https://app.example.com"]}`, at most 4 https origins with no path. `200 {"providerId":"prov-...","thumbprint":"...","time":N}`. Idempotent. A change posts a `ctl` item `{"t":"provider.updated","id":"prov-..."}` to every desktop of this relay; it changes nothing they trust until the owner re-pins.

**Roster.** `POST /v1/roster` (desktop token; `roster-request`): `{"appId":"aokie","revision":7,"thumbprints":["<sorted>", ...]}` with at most `limits.rosterMax` (16) thumbprints, possibly none. The relay validates (each 43 characters, strictly ascending bytewise, none equal to the desktop's own endpoint thumbprint), recomputes the roster hash, stores the row (desktop, appId), and revokes every phone whose `ownerDesktop` is this desktop, whose app is this app and whose thumbprint is not listed. `200 {"v":1,"hash":"...","revoked":["dev-..."],"time":N}` (`roster-response`). The revision is metadata: a value lower than the stored one from the same authenticated desktop is accepted (a reinstall restarts at 0), so there is no monotonic-revision denial of service; a revision above 2^53-1 is `400 invalid_request`. An unsorted roster, duplicates, more than 16 entries or the desktop's own thumbprint is `400 invalid_request`.

**Push registration.** `POST /v1/devices/self/push` `{"kind":"fcm","token":"<16 to 4096 printable characters>","project":"<optional>"}` gives `204`; `{"remove":true}` removes it (`push-register-request`).

## 6. Errors

Body (`error.schema.json`): `{"error":{"code":"...","message":"one sentence, safe to show a person","retryAfter":7}}`. The set of codes is closed. A client that meets an unknown code treats it by HTTP status. `retryAfter` (seconds) and the `Retry-After` header appear on 429 and 503; the two refusals of a consumer poll (the gap rule's and the bound of three, section 5.1) also have `rule` (`gap` or `in_flight`, section 5.1.1), and every other `429` has none (a poll's own is the one for an address that has failed to authenticate twenty times in a minute, the buckets of section 7.1, the limit of waiting lookups); a 401 also sends `WWW-Authenticate: Bearer realm="oaiy-relay"`. `message` is at most 200 characters. There are no stack traces, no credentials and no internal paths, ever. A client shows a relay-supplied `message` only as data. An error body carries no `time`.

| HTTP | `code` | Meaning | Retry |
|---|---|---|---|
| 400 | `invalid_request` | malformed JSON, missing or ill-typed member, bad query value, a roster that is unsorted, has duplicates or is too large | no |
| 400 | `invalid_item` | lane, TTL, `hdr` key, `hdr.sig` or `id` failed validation | no |
| 401 | `unauthorized` | missing, wrong, expired or unknown credential (deliberately one code for all of these) | no; re-enrol or refresh |
| 401 | `revoked` | the device was revoked (only after the credential verified) | no |
| 403 | `forbidden` | authenticated but not allowed: role, lane, recipient, origin, scope, slot reader | no |
| 403 | `feature_disabled` | call features are off on this relay | no |
| 404 | `not_found` | unknown recipient, item, slot, pairing, reply box, route | no |
| 405 | `method_not_allowed` | | no |
| 409 | `conflict` | duplicate `id` with different content; second rotation; state precondition | no |
| 409 | `already_answered` | pairing rendezvous already has a response | no |
| 410 | `expired` | pairing, reply box or key past its lifetime | no |
| 412 | `precondition_failed` | slot `If-Match` mismatch | after a re-read |
| 413 | `item_too_large` | body over the lane maximum, or request over 1 MiB | no |
| 415 | `unsupported_media_type` | | no |
| 422 | `unprocessable` | well-formed but wrong: ticket lane or origin mismatch, reply box not for this desktop, a small-order key | no |
| 426 | `upgrade_required` | client level below `info.minClient` | after upgrade |
| 429 | `rate_limited` | a bucket in section 7 is empty, or the poll gap rule | yes, after `Retry-After` |
| 429 | `quota_exceeded` | mailbox full | yes, after the consumer drains |
| 500 | `internal` | | yes, backoff |
| 503 | `unavailable` | database busy or locked after retries, maintenance, host overload | yes, after `Retry-After` |

A refused hold is not an error: it is a `200` with `hold.refused` (section 7.2). The compatibility routes (section 10.6) additionally use FormLogic's codes so shipped clients behave as they do today: `invalid_token` (401), `relay_target_forbidden` (403), `relay_frame_too_large` (413), `relay_backpressure` (429), `companion_unavailable` (503). They appear in the Aokie error shape `{"error":true,"code":"...","message":"..."}` (`compat-error.schema.json`) on those routes only.

## 7. Rate limits and holds

### 7.1 Buckets

| Bucket | Key | Limit | On exceed |
|---|---|---|---|
| `ip.info` | address | `GET /v1/info`, `GET /v1/health`: 60 a minute (a nonce-bearing `info` counts) | 429 |
| `ip.pair` | address | `GET` and `POST /v1/pair/{pid}...`: 30 a minute; at most 4 pairing waits held at once | 429 |
| `ip.enroll` | address | `POST /v1/enroll`: 10 a minute | 429 |
| `ip.authfail` | address | 20 failed credential verifications a minute; a request whose credential verifies is never refused by this bucket | the failing request gets 429 with `Retry-After: 60` |
| `tok.req` | token id | bucket of 120, refill 10 a second: every authenticated request except consumer polls (lookups included) | 429 |
| `tok.items` | token id | bucket of 200, refill 20 a second: items posted | per-item `rate_limited` or 429 |
| `rbx.req` | reply box | bucket of 60, refill 5 a second: every request by a reply secret | 429 |
| `adm.req` | admission `jti` | bucket of 120, refill 10 a second: compatibility requests; the admission mint itself is 30 a minute per token | 429 |
| `pid.get` | pairing id | 60 GETs in its lifetime while it is open or answered (an outcome is read without counting: Interpretation 50) | 429 |
| `pid.resp` | pairing id | 3 responses accepted; a fourth is `409 already_answered` | |
| `kid.fail` | enrolment key | 5 failed proofs burn it | 401 |
| `tokid.fail` | (token id, address) | 20 wrong secrets an hour lock that id for that address for 15 minutes; the real device from another address is unaffected | 401 |

Clients honour `Retry-After` with an upper bound of 120 seconds and add up to 20 percent jitter. **Client address.** The key is `REMOTE_ADDR`, IPv6 reduced to its /64 and `::ffff:a.b.c.d` reduced to `a.b.c.d`. A forwarding header (for example `X-Forwarded-For`) is honoured only when `REMOTE_ADDR` is inside the configured trusted proxies, taking the rightmost address that is not itself a trusted proxy; otherwise it is ignored.

### 7.2 The hold registry

A hold is any request that may wait longer than zero seconds. A held request pins one worker for as long as it waits, so every hold of every kind is counted, superseded per principal and refusable.

| Hold | Principal | Class | Supersede | Wait cap |
|---|---|---|---|---|
| consumer poll, `GET /v1/poll` | device id | core if role `desktop`, otherwise edge | a newer consumer poll of the same device ends the older within 250 ms | `wait.max` |
| lookup with `wait > 0` (provider only) | device id | edge | none among lookups; at most 4 per device | 8 s |
| reply-box poll, `GET /v1/rbx/{rid}/poll` | `rid` | edge | one per box: a newer poll ends the older | `wait.max` |
| pairing wait, `GET /v1/pair/{pid}?wait=` | `pid` | edge | one per `pid` | `wait.max` |
| Aokie stream and frames wait | (desktop, appId, party) | core | one per party | 20 s |
| admin hold (calibration) | admin | exempt | none | 35 s |

With `W` the worker pool (`capacity.workers`, 5 until measured): `held_soft = max(2, floor(0.6 * W))` and `held_hard = max(3, W - 1)`. An edge hold is refused when the live count is at or above `held_soft`; a core hold when it is at or above `held_hard`. For polls, lookups, box polls, pairing waits and frame waits a refusal is a degradation, not an error: the relay runs the fetch once as if `wait=0` and answers `200` with `X-OAIY-Hold: refused` and `"hold":{"refused":true,"retryAfter":2}` (the smaller of 2 and `info.wait.fallbackS`: a relay configured with a fallback of 1 says 1); a client short-polls at `retryAfter` (2 s, doubling up to `info.wait.fallbackS`, 5: 2, 4, 5, 5...) with jitter and asks for a hold again on every request. A `wait=0` request is never refused. For the stream route (a core hold) refusal at the hard limit is `503 companion_unavailable` with `Retry-After: 2`. One credential cannot pin more than: a phone token, its inbox poll and its stream (two: a poll that a newer one supersedes still runs for up to a step, so at most three polls of one credential may run at once, and three streams or frames waits of one party, the fourth being `429` before the request does any database work of its own: after the check of the credential for a poll and after one read of the party's bucket row for a stream open; Interpretations 53 and 58); a reply secret, one; a `pid`, one, and at most four pairing waits per address; a provider token, four short lookups; a desktop token, its own poll and the plugin's stream.

## 8. Versioning, capability negotiation and the identity proof

`GET /v1/info` (`info.schema.json`; no authentication; `Cache-Control: public, max-age=60` without a nonce; strong ETag; `If-None-Match` gives `304`) is a static document:

```json
{"protocol":"oaiy-relay/1","minClient":1,"relayId":"rly-...","relayKey":{"algorithm":"ed25519","publicKey":"...","thumbprint":"..."},
 "software":{"name":"oaiy-relay","version":"0.1.0"},"features":["poll","items","presence","methods.post-forms"],
 "wait":{"default":20,"max":20,"pollGapMs":250,"fallbackS":5},"presenceWindow":60,
 "limits":{"batchItems":64,"batchBytes":1048576,"mailboxItems":512,"mailboxBytes":8388608,"bulkShare":0.75,"hdrBytes":512,
           "held":{"soft":3,"hard":4,"measured":false},"lanes":{"cmd":{"body":32768,"ttl":{"default":60,"min":1,"max":300}}}}}
```

The full example of the design, with every optional member, is `A6b` in `vectors.json`. The body has no `time` member, so it is static and its signature can be cached. `features` lists only what the relay implements and has enabled: `poll`, `items`, `slots`, `presence`, `replyboxes`, `tickets`, `pairing.v3`, `methods.post-forms`, and, only when the owner has enabled call features, `call`, `admission.aokie-adm-v2`, `compat.aokie-companion-relay` (with the `ring` and `sig` lanes and `call.*` slots); `compat.sse-framed-poll` only when the streaming probe passed on this host; `push.fcm` only when configured. `limits.held` shows the soft and hard hold limits and whether the pool was measured.

1. **Static signature (integrity and feature discovery, not identity).** The response carries `X-OAIY-Sig: <b64u Ed25519 signature over "oaiy/relay/1/info" || 0x00 || exact body bytes>`. It proves the bytes were once signed by the relay key; anyone can copy the body and the signature and serve them, so it proves nothing about who is answering now.
2. **Interactive proof (identity).** A request carrying `X-OAIY-Nonce: <b64u of 16 to 32 random bytes>` (22 to 43 characters; any other length is `400 invalid_request`) is answered with the same body, `Cache-Control: no-store`, and `X-OAIY-Proof: b64u(Ed25519(relay key, "oaiy/relay/1/info-proof" || 0x00 || nonce bytes || SHA-256(body) (32 bytes) || ASCII decimal of the X-OAIY-Time value))`. A client verifies that `relayKey.publicKey` hashes to the thumbprint it pinned (`f` in the enrolment or pairing key, or `offer.relay.fingerprint` for a typed pairing), that the proof verifies over its own nonce, and that `X-OAIY-Time` is the value the proof covers. Vectors `A6` and `A6b`: a replayed body and static signature with a new nonce must fail.
3. **When a client proves.** Before enrolment, before the phone's pairing, at the provider's link, and before sending a bearer on a connection it has not proved: at process start, after any failure or backoff of 60 s or more, after a network change, and at least every 300 s while polling. A client that cannot obtain a valid proof does not send its token and reports the relay as "not who it was".
4. **What the proof does and does not defeat.** It defeats a replaced server (a lapsed or hijacked name pointing at a host that never held the relay key). It does not detect a live forwarding proxy that holds a valid certificate for the relay's name and relays the challenge to the real relay: there is no channel binding to TLS.
5. Clients cache the static `info` for 10 minutes and re-read it on start and on a `426`.

## 9. Authentication

### 9.1 Device capability tokens

1. **Generation.** `id` = 8 random bytes, `secret` = 32 random bytes, both from the operating system CSPRNG. Token string: `"oaiyrt1." + b64u(id) + "." + b64u(secret)`, always 63 characters. Vector `A2`.
2. **Storage.** The relay stores `SHA-256(secret bytes)` (or `HMAC-SHA-256` with an optional server pepper), the id, the device, and times; nothing else. The secret bytes are the 32 raw bytes that the 43-character secret decodes to, not the 43 characters (vector `A2`, `secretSha256`). A copy of the database yields no credential.
3. **Verification, in this order, with the same `401 unauthorized` and body for every failure:** (a) strict parse (prefix, two dots, lengths 11 and 43, base64url alphabet, canonical last characters); (b) look up by `id`; if absent, hash a dummy secret and compare, so timing does not reveal which ids exist; (c) constant-time comparison of the stored hash with `SHA-256(secret)`; (d) `revoked_at` null and `not_after` in the future (or null); (e) the device not revoked; (f) the route's role and scope allow it. A token whose secret verified but whose device or token was revoked is `401 revoked`. Every failure counts against `ip.authfail` and `tokid.fail`.
4. **Carriage.** `Authorization: Bearer` only, with the scheme matched case-insensitively and one space. The relay reads it from `HTTP_AUTHORIZATION`, `REDIRECT_HTTP_AUTHORIZATION` and `getallheaders()`, in that order, because FastCGI-family stacks drop the header unless the vhost passes it. It never reads a URL or a cookie and never logs the header. `GET /v1/health` reports `authHeaderSeen`. A missing header is counted separately from a wrong token in admin status; on the wire both are the same `401`.
5. **Rotation and revocation:** section 5.4. Rotation every 90 days is recommended.
6. **Scope.** One token belongs to exactly one device and role; the route table in section 5 fixes what each role may call.
7. **Send discipline.** A client sends the token only after a fresh identity proof (section 8).

Replay protection is by layer: a request is protected by TLS (item posts are idempotent on `id`, polls are reads); an item at the relay by `(mailbox, lane, sender, id)` uniqueness for 10 minutes after ack or expiry; an item at the desktop by a persisted replay cache of authenticated `(signer, id)` pairs retained for `(exp - iat) + 120` seconds in provider time; a pairing response by one-use `nonce` and `jti`, one accepted response and a transcript-bound MAC; a ticket by a single-use `jti`; an admission by its 90 second life.

### 9.2 Provider tickets: JWS, EdDSA

A ticket lets a browser reach the relay after a provider has vouched for it. It is a JWS Compact Serialization (RFC 7515) with `alg` `EdDSA` over Ed25519 (RFC 8037). The signature is over the ASCII bytes of `b64u(header) + "." + b64u(payload)` exactly as transmitted; nothing is canonicalised. Vector `A1` reproduces the RFC 8037 appendix A.4 example as an anchor; `A9` is a complete ticket.

Protected header (`ticket-header.schema.json`): `{"alg":"EdDSA","typ":"oaiy-ticket+jwt","kid":"<thumbprint of the provider's Ed25519 key>"}` and nothing else (`crit`, `jku`, `jwk`, `x5u`, `x5c` are refused). Claims (`ticket-claims.schema.json`): `iss` the provider id, `aud` the relay id (a ticket for another relay is refused), `sub` an opaque member reference of at most 64 characters with no personal data, `iat` and `exp` (`exp - iat <= 300`), `jti` an id of at most 64 characters (single use), `lane` (`ai` in v1), `dev` the desktop's device id the browser may reach, `org` the browser origin, `eph` b64u of SHA-256 of the browser's ephemeral X25519 public key.

The relay verifies, and any failure is `401 unauthorized` (or `403`/`422` where noted): header `alg` exactly `EdDSA` (so `none`, `HS256` and every other algorithm confusion is refused), no `crit`, `jku`, `jwk`, `x5u`, `x5c`; `kid` matches a registered provider; the signature verifies; `aud` equals this relay; `iat <= now + 30` and `exp + 30 > now` and `exp - iat <= 300`; `lane` allowed; `dev` is an active desktop of this relay (`422` otherwise); the request's `Origin` header equals `org` and is one of the provider's registered origins (`403` otherwise); `jti` not seen. A ticket is single-use for creating one reply box. The desktop performs its own, independent verification of the same ticket.

### 9.3 The other credentials

- **Admission bearer** (`aokie-adm-v2`): section 10.6.
- **Reply secret**: 32 random bytes chosen by the browser, b64u (43 characters), sent as `Authorization: Bearer <secret>` to `/v1/rbx/{rid}/...`; the relay stores SHA-256 of it with the reply box; lifetime is the box's TTL (default 900 s), ended earlier by `DELETE`.
- **Pairing rendezvous**: the `pid` itself is the capability (128 bits, derived from the secret, section 10.1).
- **Enrolment key**: section 10.2.
- **Admin token**: `oaiyadm1.` + b64u(8 bytes) + `.` + b64u(32 bytes); the relay stores a hash; it opens the status page and the calibration routes and nothing else (it cannot mint a desktop key).

### 9.4 Clocks: which clock judges what

| Check | Window | Whose clock |
|---|---|---|
| ticket `iat`/`exp` at the relay (advisory only) | 30 s | relay |
| admission verification at the relay | 30 s | relay |
| command envelope `iat`/`exp` at the desktop | `[iat - 30, exp + 30]` | provider clock |
| ticket `iat`/`exp` at the desktop | `[iat - 30, exp + 30]` | provider clock |
| replay cache retention | `(exp - iat) + 120 s` from first sight, an absolute provider-time deadline `retain_until = exp + 60` and never shortened | provider clock |
| pairing offer and response windows | 30 s | relay-corrected time at both ends |
| enrolment key expiry | 0 | relay |
| ring `expiresAt` on a relay-profile phone | 0 | relay-corrected time |

The provider clock is the desktop's offset to the provider, taken from the provider's own TLS responses (the HTTP `Date` header or a `serverTime` member), median of the last five samples, slewed by at most 1 second a minute, applied to a monotonic local clock. An offset older than 150 s is `clock_unknown`; `|offset| > 60 s` is `clock_mismatch`; in either case signed items are refused and nothing signed is pruned.

## 10. Formats

### 10.1 Pairing v3 (a phone without FormLogic)

**Secret.** `s` is 16 bytes from the desktop's CSPRNG, used once, never sent to the relay.

**Pairing key** (QR or deep link): `oaiy://pair?v=3&u=<relay base URL, percent-encoded>&f=<relay key thumbprint, 43 chars>&s=<b64u of s, 22 chars>&x=<expiry, Unix seconds>` (`common#pairingUri`). Parse rules: scheme and host exactly as shown; `v` must be `3`; `u` an https URL with no userinfo, query or fragment; `s` exactly 22 characters decoding to 16 bytes; `f` and `x` optional; unknown parameters ignored; total length at most 512. A deep link or a scanned QR never starts pairing by itself: it opens a full-screen confirmation, and it never replaces or activates an existing relay profile without a second confirmation.

**Typed code** (`common#typedCode`): 28 characters: `s` as Crockford base32 (26 characters carrying 128 bits, the last two bits zero), then a 2 character check = the Crockford base32 encoding of the first 10 bits of `SHA-256("oaiy/pairing/3/typed" || 0x00 || s)` (`s` being its 16 raw bytes), shown in seven groups of four separated by dashes. Input is normalised (upper case, `I` and `L` read as `1`, `O` as `0`, dashes and spaces removed, `U` refused) and the check is verified locally before any network call. The typed route also asks for the relay's address (the host name), because the code carries only `s`; the phone builds `https://<host>`, fetches the offer from it and requires `offer.relay.url` to equal that URL and the relay's fresh info proof to be made by the key whose thumbprint equals `offer.relay.fingerprint`.

**Derivations** (HKDF-SHA256, RFC 5869; `salt` is the UTF-8 string `oaiy/pairing/3`; `IKM` is `s`): `pid = HKDF(info = "rendezvous", L = 16)`, which is 16 raw bytes; it is written as b64u (22 characters) in URLs and JSON, and `A3` records both spellings (`pid`, `pidHex`); `mac_key = HKDF(info = "mac", L = 32)`, which never leaves the two endpoints. Vector `A3`.

**Offer** (`pairing-offer.schema.json`): canonical JSON with exactly the members `kind` (`aokie_mobile_pairing`), `schemaVersion` (`3`), `appId`, `desktopConnectionId` (the desktop's relay `deviceId`), `desktopName` (at most 60 characters, control characters removed), `desktopEndpointKey`, `desktopX25519`, `hostIdentity` (`{"ed25519","thumbprint","x25519"}`: the phone pins them), `nonce` (b64u of 32 random bytes), `jti` (`pair-` + an id), `issuedAt`, `expiresAt` (`expiresAt - issuedAt = 600`), `relay` (`{"url","fingerprint"}`). The offer is stored on the relay as the exact text plus `mac = b64u(HMAC-SHA256(mac_key, "oaiy/pairing/3/offer-mac" || 0x00 || offer text bytes))`. The phone verifies the MAC over the received text and does not re-serialise it. The offer of `A3` is 778 bytes.

**Response** (`pairing-response.schema.json`): `{"kind":"aokie_mobile_pairing_response","schemaVersion":3,"claims":{...},"signature":"<b64u>","mac":"<b64u>"}`. `claims` (`pairing-claims.schema.json`, canonical form for signing) holds `appId`, `desktopConnectionId`, `desktopKeyThumbprint`, `deviceId`, optional `displayName` (at most 60 characters), `mobileEndpointKey`, `mobileX25519`, `pairingNonce`, `jti`, `issuedAt`, `expiresAt` (at most `issuedAt + 120`). `signature` is Ed25519 by the phone's endpoint key over `"oaiy/pairing/3/response" || 0x00 || canonical(claims)`; `mac` is HMAC-SHA256 under `mac_key` over `"oaiy/pairing/3/response-mac" || 0x00 || canonical(claims)`. Both are required.

**Short authentication string.** `sas_raw = HKDF-SHA256(IKM = desktopEd25519Pub || phoneEd25519Pub (64 bytes), salt = nonce bytes, info = "oaiy/pairing/3/sas" || 0x00 || pid, L = 8)`, where `desktopEd25519Pub` is the 32 raw bytes of the desktop endpoint key (`offer.desktopEndpointKey.publicKey` decoded), `phoneEd25519Pub` the 32 raw bytes of the phone endpoint key (`claims.mobileEndpointKey.publicKey` decoded), `nonce bytes` the 32 raw bytes of the pairing nonce (`offer.nonce` decoded), and `pid` the **raw 16 bytes** of the rendezvous id, not its 22-character b64u text and not hex: `info` is the 18 ASCII bytes of `oaiy/pairing/3/sas`, one zero byte and those 16 bytes, 35 bytes in all. Reading `pid` as the 22-character text makes a 41-byte `info` and a different, wrong SAS; `extras.sasNegative` in `vectors.json` records what that wrong reading produces for the inputs of `A3` (`24b574fd2e0d1e24` where the right value is `3563599914bdf7f9`), so that an implementation can prove it is not making that mistake (Interpretation 21). Take the top 60 bits of the 8 bytes and write them as 12 Crockford base32 characters. The phone shows 13 characters: the 12 and one check character `C = Crockford32[ SHA-256("oaiy/pairing/3/sas-check" || 0x00 || the 12 characters as ASCII)[0] >> 3 ]`, grouped `XXXX-XXXX-XXXX-C` (`common#sasCode`). The check is a public function of the twelve; it exists so that a single mistyped character is caught locally and does not cost one of the owner's three attempts.

**Approval receipt** (`approval-receipt.schema.json`). On approval the host signs `Ed25519(desktopEndpointKey, "oaiy/pairing/3/approval" || 0x00 || canonical({"appId","grants" (sorted),"issuedAt","phoneThumbprint","pid"}))` (here `pid` is a JSON string holding the 22-character b64u text) and sends it in the decision (`pairing-decision.schema.json`, member `receipt` `{"issuedAt","signature"}`). The relay stores it and returns it beside `sealedToken`, **with the grants it was signed over**: `receipt` is `{"issuedAt","signature","grants"}`, where `grants` is the sorted set (code-point order, no repeats) that is in the canonical document above, which is the one thing the phone cannot know otherwise (the desktop signs the grants, the phone never sees the decision). The phone builds the canonical document from exactly the returned `grants`, its own `appId`, the `pid`, the returned `issuedAt` and the thumbprint of its own endpoint key, verifies the signature with the desktop key it pinned from the MAC'd offer, and refuses the receipt (and the whole pairing) when it does not verify, when `grants` is missing, unsorted or has a repeat, or when it holds a name outside the fourteen of section 4.14: the signature covers the grants, so a relay that returns others fails the verification, and a phone that stores a grant it does not know would break every admission (Interpretation 60).

**The exchange.** (1) `POST /v1/pair` (desktop token; `pairing-create-request`: `pid`, `offer` text of at most 4,096 bytes, `mac`, `ttl`, `appId`, `desktopThumbprint`) opens a rendezvous; the relay parses the offer text only to check that its `appId` and `desktopEndpointKey.thumbprint` equal the request's two fields, stores the text unchanged, answers `201 {"pid","exp","time"}`, and `409 conflict` if `pid` exists (the same desktop's identical request, a retry of one whose answer was lost, gets the original `201` instead: Interpretation 51). (2) `GET /v1/pair/{pid}` (no credential) answers `pairing-fetch-response`; an unknown or expired `pid` is one `404 not_found` with an identical body and timing. (3) The phone shows the owner the relay host and the desktop's name before anything is posted. (4) `POST /v1/pair/{pid}/response` `{"response":"<JSON text, at most 8192>"}` answers `202 {"state":"answered","time":N}`; a second, different post is `409 already_answered` (the identical post again, a retry of one whose `202` was lost, is `202` again: Interpretation 51); the relay posts one `pair` item (`id` = `pid`, body = the response text) to the desktop inbox; the phone waits with `GET /v1/pair/{pid}?wait=20&state=answered`. (5) The desktop verifies (shape, identifiers, lifetime against relay time with 30 s skew, nonce and `jti` not consumed, live challenge, binding to the offer, key not revoked, `mobileX25519` of 32 bytes and not of small order, the MAC in constant time, and the signature last with strict verification) and on failure calls `POST /v1/pair/{pid}/reject {"reason":"..."}`, which returns the rendezvous to `open` while fewer than 3 rejects have happened. (6) The owner types the 13 character code; three wrong 12-character entries deny the pending item and burn the rendezvous; an incomplete entry or a wrong check character is not an attempt. (7) `POST /v1/pair/{pid}/decision` (desktop token) `{"approve":true,"phone":{"ed25519","x25519","thumbprint"},"name","appId","grants":[...],"receipt":{"issuedAt","signature"}}` or `{"approve":false}`; the default grants exclude `monitor`, `consult` and `takeover`. (8) On approval the relay rejects a small-order phone X25519 key (`422`), creates the phone device, generates a token, and stores `sealed = crypto_box_seal(token, phoneX25519)` (libsodium `sodium_crypto_box_seal`); the plaintext token exists in the request's memory and nowhere else. (9) The phone's poll returns `{"v":1,"state":"approved","deviceId","sealedToken","receipt":{"issuedAt","signature","grants"},"time"}` (or `{"state":"denied"}`); it verifies the receipt over exactly the returned `grants` (and refuses a grant name it does not know), opens the box, stores the profile, and pins the desktop endpoint key and the host identity from the MAC-verified offer as the only source of its peer pin. The rendezvous is deleted 10 minutes after the phone read a terminal state, or at expiry.

Relay-side states: `open -> answered -> approved | denied`; `answered -> open` by `reject` (at most 3 times, then `expired`); `open | answered -> expired` at `exp` (at most 900 s after creation). Limits: offer 4,096 bytes, response 8,192 bytes, 3 accepted responses, 60 GETs, lifetime 900 s, 16 pending approvals at once.

**The rendezvous as the relay serves it** (interpretations 25 to 35 give the reasons). Every operation in every state, as the answer the caller gets (`-` cannot happen: the state has no such request):

| Operation | open | answered | approved | denied | ended (burned, third reject) | past `exp` |
|---|---|---|---|---|---|---|
| phone `GET /v1/pair/{pid}` | 200 | 200 | 200 with the sealed token | 200 `denied` | 404 | 404 |
| phone `POST .../response` | 202 | 409 `already_answered`, or 202 again for the very response it holds | 409, or 202 again for the very response it took | the same | 404 | 404 |
| desktop `POST .../decision` approve | 409 `conflict` | 200 | 200 (the same approval again), 409 for another key | 409 | 410 `expired` | 410 |
| desktop `POST .../decision` deny | 409 | 200 | 409 | 200 (again) | 410 | 410 |
| desktop `POST .../reject` | 409 | 200 (`open`, or `expired` on the third) | 409 | 409 | 410 | 410 |
| desktop `POST .../burn` | 200 | 200 | 409 | 200 | 200 (already ended) | 410 |

An unknown pid is the same 404 as an ended or expired one for the phone, and another desktop's pid is the same 404 as an unknown one for a desktop. Answers: `POST /v1/pair` `201` `{"pid","exp","time"}` (`pairing-create-response`); `GET` `pairing-fetch-response`; the response `202` `{"state":"answered","time"}`; the decision `200` `{"v":1,"state":"approved"|"denied","deviceId"?,"time"}` (`pairing-decision-response`); reject and burn `200` `{"v":1,"state":"open"|"expired","time"}` (`pairing-state-response`). The phone's two routes count against `ip.pair` (30 a minute per address); the desktop's three are its token's (`tok.req`). A held `GET` (`wait` with a live pid) is an edge hold counted once by its pid, at most 4 per address; when the pool is nearly full it is answered at once with `hold.refused`. The recorded ceremony is `fixtures/pairing-ceremony.json`.

### 10.2 Enrolment: the desktop and the provider

**Enrolment key** (`common#enrollUri`): `oaiy://enroll?v=1&u=<relay base URL>&f=<relay key thumbprint>&k=<kid, 11 chars>&s=<b64u of s, 22 chars>&r=<desktop|provider>&x=<expiry>`. `s` is 16 random bytes. With `salt = "oaiy/enroll/1"` and `IKM = s`: `kid = b64u(HKDF(info="id", L=8))`, and `seed = HKDF(info="sig", L=32)` is an Ed25519 seed. The relay stores the derived Ed25519 public key only, so a copy of the database yields nothing redeemable. A key is single-use, valid for one hour by default and at most 24. A relay admits at most `limits.desktops` (default 2) desktop devices.

**Redeeming.** `POST /v1/enroll` (`enroll-request.schema.json`) body `{"kid":"...","role":"desktop","name":"<=60","n":"<b64u of 16 random bytes>","keys":{"ed25519":"<b64u>","x25519":"<b64u>"}}` and the request header `X-OAIY-Proof: b64u(Ed25519(seed, "oaiy/relay/1/enroll" || 0x00 || raw request body bytes))`. The secret itself is never transmitted. The relay verifies the signature over the bytes it received, marks the key used with one conditional update (so two racing requests cannot both win), creates the device and its token and answers `201` (`enroll-response.schema.json`) `{"deviceId":"dev-...","token":"oaiyrt1....","relayId":"rly-...","time":N}`. Every failure (unknown, used, expired, wrong role, bad proof) is the same `401 unauthorized`; five failed proofs against one `kid` burn it; a small-order X25519 or Ed25519 key is `422`. The client verified a fresh identity proof before sending anything. Vector `A7`.

**Provider registration and the desktop's pin.** After redeeming, a provider calls `POST /v1/providers` with its origins. The desktop does not take the relay's word for the provider's keys: it fetches them from the provider over the existing authenticated TLS link, compares them with what the relay registered, shows the owner the fingerprint, rejects a small-order key, and stores the pin only after the owner confirms.

**Provider key rotation.** A later change of provider keys arrives as a `ctl` hint and is accepted without asking only if it carries a rotation statement signed by the currently pinned Ed25519 key. The statement (`rotation-statement.schema.json`) is shipped bytes: `{"v":1,"prev":"<thumbprint of the key being replaced>","new":{"ed25519":"...","thumbprint":"...","x25519":"..."},"serial":n,"iat":N,"exp":N}` and `signature = Ed25519(K_prev, "oaiy/relay/1/provider-rotate" || 0x00 || bytes)` (`bytes` being the statement's text bytes, the decoded content of `b` below), delivered as `ctl` `{"t":"provider.rotated","b":"<b64u bytes>","s":"<b64u signature>"}`. The desktop accepts it only when `prev` equals the thumbprint it has pinned, `serial` is greater than the last accepted serial for that provider, `exp - iat` is at most 24 hours, the time window holds in provider time, and the signature verifies with strict verification. Vector `A10`.

### 10.3 Authority envelopes: commands and results

Two standard operations are combined: an Ed25519 signature for authority and a libsodium sealed box (`crypto_box_seal`) for confidentiality to the desktop's published X25519 key. Every place that takes a peer's public key for a Diffie-Hellman or a signature refuses one of small order (vector `A12`): for X25519, after masking bit 255, a value that reduced modulo p = 2^255 - 19 is 0, 1, p-1, or one of the two order-8 values; equivalently any key whose shared secret would be all zero. For Ed25519, a pinned or registered public key of small order is refused, and every verification against a pinned key uses strict verification.

Signed bytes are shipped, not re-derived:

```
container = {"k":"<thumbprint of the signer's Ed25519 key>","b":"<b64u of the exact signed bytes>","s":"<b64u Ed25519 signature>"[,"p":"<b64u padding>"]}
signature = Ed25519(signer key, "oaiy/relay/1/cmd" || 0x00 || bytes)        (results: "oaiy/relay/1/res"; sync: "oaiy/relay/1/sync")
            where bytes = the exact signed bytes, i.e. the decoded content of "b", not the b64u text of "b"
sealed    = crypto_box_seal(container as UTF-8 JSON text, recipient X25519 public key)
item      = {to, lane:"cmd"|"res", id, ttl, hdr:{"ct":"sealed1"}, body: b64u(sealed)}
```

`container.schema.json` allows only `k`, `b`, `s`, `p`. The receiver verifies the signature over the decoded bytes and only then parses them. The optional member `p` is random padding that a signer SHOULD add so the container's length is a multiple of 256 bytes; verifiers ignore it. Vector `A8` (the sealing step is randomised and has no fixed vector).

**Command document** (`command.schema.json`; the bytes; the signer is the provider): `v` (1), `id` (the command id; equals the item `id` and any `hdr.re` on the result), `dev` (the desktop's relay device id), `to` (the desktop's provider instance id), `connector`, `command`, `payload` (an object of at most 16 KiB), `idem` (the provider's idempotency key), `iat`, `exp` (signer's clock; `exp - iat <= 300`), `src` (the provider id), `uid` (opaque member reference, at most 64 characters, audit only), and `dep`, which is reserved: a v1 signer never sets it and a v1 verifier refuses a document that carries it (`failed/unsupported`).

**Result document** (`result.schema.json`): `{"v":1,"re":"<command id>","dev":"<desktop device id>","status":"done"|"failed","result":{...}|null,"error":{...}|null,"at":N}`, signed by the host identity and sealed to the provider's X25519 key. A `done` result has a null `error`; a `failed` result has an `error` object with a `code`.

**Verification on the desktop, in this order.** Any step failing before step 4 completes drops the item; afterwards a coded, signed failure result is returned. (1) Lane `cmd`, `hdr.ct` is `sealed1`, body decodes, size within the lane cap. (2) Open the sealed box with the host's X25519 identity. (3) Parse the container; `k` must equal the thumbprint of a pinned provider signing key. (4) Verify the signature over the decoded bytes strictly. From here the item is authenticated. (5) Parse the bytes: `v` is 1; `id` equals the item id; `dev` and `to` are this desktop; `exp - iat <= 300`; no `dep`. (6) Time, in provider time: `clock_unknown` or `clock_mismatch` return `failed` with that code; outside `[iat - 30, exp + 30]` returns `failed`/`expired`. (7) Replay and ledger: only now look the signer (the `k` of step 3) and the `id` up in the persisted cache and, if absent, add the pair before executing; a repeat after completion resends the stored result. (8) Authorisation: the per-connector allow-list decides; call-control commands MUST carry `payload.callId`, a missing id is `failed`/`call_id_required`. (9) Execute with the idempotency key `relay-command-<id>`. (10) Sign the result, seal it to the provider's X25519 key, post it as a `res` item (`id` = `res-<command id>`, `hdr.re` = the command id, TTL 300 s).

### 10.4 Sealed chat through a reply box and a ticket

The chat envelope is the existing NaCl `crypto_box` tunnel. (1) The browser asks the provider for a ticket. (2) `POST /v1/replyboxes` with `Authorization: Bearer <ticket>` and `{"rid":"<b64u 16 bytes>","h":"<b64u SHA-256 of a 32-byte secret the browser keeps>","ttl":900}` (`replybox-request`) answers `201 {"rid","exp","time"}` (`replybox-response`); the relay limits live boxes to 2 per ticket `sub` and 8 per desktop. (3) `POST /v1/rbx/{rid}/items` (Bearer reply secret; `rbx-item-request.schema.json`) with lane `ai` or `ai.in`, `hdr` `{"ct":"tunnel1","eph":"<standard base64 ephPub>"}` and the standard-base64 envelope as `body`. (4) The desktop opens the envelope, requires the ticket inside it, verifies it independently in provider time, and posts sealed frames to `rbx:<rid>` as lane `ai.out`. (5) `GET /v1/rbx/{rid}/poll?since=&wait=20` returns frames with the poll semantics of section 5.1; `POST /v1/rbx/{rid}/end` ends the box. (6) Stream integrity: the browser accepts a desktop frame only when its counter is exactly the previous counter plus one, and the terminal state comes only from a sealed `final` or `error` frame.

**CORS.** Only the ticket and reply box routes answer cross-origin requests. `OPTIONS` returns `204` with `Access-Control-Allow-Origin: <the exact request origin, only if it is in the registered origins of some provider>` (never `*`), `Access-Control-Allow-Methods: GET, POST, DELETE, OPTIONS`, `Access-Control-Allow-Headers: Authorization, Content-Type, X-OAIY-Client`, `Access-Control-Max-Age: 600`, `Vary: Origin`; no `Access-Control-Allow-Credentials`. Every other route sends no CORS headers at all. If an `Origin` header is present on a reply-box request it must be in the list (`403 forbidden` otherwise); an absent `Origin` is accepted on `/v1/rbx/*` and never on `POST /v1/replyboxes`.

### 10.5 Ring hints

A `ring` item's `body` (`ring.schema.json`) is a JSON object whose members are exactly the FCM `data` map, every value a string:

| `aokieClass` | Required members (all strings) |
|---|---|
| `voice_offer` | `schemaVersion` `"1"`, `eventId`, `offerId`, `appId`, `callId`, `callEpoch`, `ownerEpoch`, `expiresAt` |
| `voice_offer_cancel` | `schemaVersion` `"1"`, `eventId`, `offerId`, optional `reason` (1 to 120 characters, no control characters) |
| `assistance_offer` | `schemaVersion` `"1"`, `eventId`, `appId`, `requestId`, `callId`, `callEpoch`, `ownerEpoch`, `expiresAt` |
| `informational` | `schemaVersion` `"1"`, `eventId`, `title` (at most 80), `body` (at most 240), `expiresAt` |

Ids match `[A-Za-z0-9_.:-]{1,200}`; `callEpoch` is 1 to 2^53-1; `ownerEpoch` 0 to 2^53-1; `expiresAt` is Unix seconds, later than now and at most now + 300 (86,400 for informational); no other members. **Signature.** A `ring` item carries `hdr.sig = b64u(Ed25519(host identity, "oaiy/relay/1/ring" || 0x00 || body text exactly as posted))`. A relay-profile phone drops a ring whose signature does not verify against the host identity it pinned at pairing. `expiresAt` is judged in relay-corrected time. Push and ring data are wake hints and never authority: no SDP, ICE, token, caption or caller number. Vector `A11`.

### 10.6 The admission issuer and the Aokie compatibility routes

Present only when call features are enabled (`403 feature_disabled` otherwise).

**Token.** `aokie-adm-v2.` + lowercase hex of the claims JSON + `.` + lowercase hex of `HMAC-SHA256(admission secret, exact claims JSON bytes)`. Claims (`admission-claims.schema.json`; in this order): `aud` = `aokie-v2-gateway`, `appId`, `subjectId`, `role` (`mobile` or `plugin`), `holderKeyThumbprint`, then for a mobile `expectedPeerKeyThumbprint`, for a plugin `approvedPeerKeyThumbprints`, `peerRosterRevision`, `peerRosterHash`, then `scopes`, `dsk` (the device id of the desktop the party belongs to; read only by the relay), `exp`, `jti` (`adm_` plus 32 hex characters). TTL 90 seconds by default and never more than 300. Vectors `A4` (888 characters for a phone) and `A4b` (a plugin token is 964 characters for one phone and grows by 92 per phone: 2,344 for sixteen). The roster hash is `b64u(SHA-256("aokie/v2/peer-roster" || 0x00 || {"approvedPeerKeyThumbprints":[...sorted],"peerRosterRevision":N}))` in canonical form; vector `A0` checks it against the Aokie README's own example.

**`POST /v1/admission`** (alias `POST /v1/aokie-companion/admission`; 30 a minute per token). Plugin admission (desktop token; `admission-plugin-request`): validation in order: `appId` and `pluginId` are safe ids; `endpointPublicKey` is `{algorithm:"ed25519", publicKey, thumbprint}` with a canonical 32-byte key of no small order and a thumbprint that recomputes, and `holderKeyThumbprint` equals it; `approvedPeerKeyThumbprints` has 1 to 16 entries, each a valid thumbprint, strictly ascending, none equal to the holder; `peerRosterRevision` is an integer from 1 to 2^53-1; `peerRosterHash` recomputes. The admission changes nothing in the roster registry. Issued with role `plugin`, scopes `["state_read","rtc_signal"]`, TTL 90. Response (`admission-plugin-response.schema.json`): exactly `accessToken`, `tokenType` `Bearer`, `expiresIn`, `expiresAt`, `gatewayUrl` (a syntactically valid `wss://<relay host>/v2/realtime` that is never dialled), `appId`, `subjectId`, `role`, `scopes`, `device`, `iceServers`, `relayOnly`, `turnCredentialExpiresAt`, `endpointPublicKey`, `holderKeyThumbprint`, `approvedPeerKeyThumbprints`, `peerRosterRevision`, `peerRosterHash` and `relay` (`{"challengeUrl","framesUrl","streamUrl"}`, plus `"mode":"poll"` for a poll-mode carrier), and no other member: the plugin's decoder is strict. It never emits `desktopConnection` or `scopeCompatibility`. The three relay URLs are byte-identical in every admission and carry no per-admission query string. Mobile admission (phone token; `admission-mobile-request`, `admission-mobile-response`): the token's device must be a phone; `deviceId` must equal it; `holderKeyThumbprint` must equal the phone's registered thumbprint; `appId` must equal the pairing's; the roster row, when it exists, must list the phone's thumbprint (otherwise `403 forbidden`); `supportedTransports` (1 to 8 short strings; absent means `[relay]`, a member that is there and malformed is `400`) is judged last, after the request itself: `relay` is served as the framed stream when this host has passed the streaming probe (interpretation 40), `relay-poll` as `relay.mode: "poll"`, and a list with neither is `422 unprocessable`. The phone must belong to a live desktop, have a recorded expected peer (its pairing) and hold `state_read`, else `403` (interpretation 41); unknown grant names are dropped from `scopes` and `device.grants`. With call features off the answer is `403 feature_disabled`, before the body is read. Errors of the alias are in the Aokie shape (interpretation 37). A phone treats the relay-supplied `expectedPeerKeyThumbprint`, `iceServers`, `scopes` and `device` as advisory: its desktop pin comes only from the MAC-verified offer, and a different expected peer is a hard error.

**ICE and TURN** (`ice-server.schema.json`). A STUN entry is `{"urls":["stun:..."],"username":"","credential":""}`: the plugin's decoder requires both members and refuses a value in either, and an `expiresAt`. Each TURN entry is `{"urls":[...],"username":"<exp>:<opaque id>","credential":"<base64(HMAC-SHA1(secret, username))>","expiresAt":<exp>}` with `exp` 31 seconds to 24 hours ahead (this relay: the start of a window of a sixth of `turn.ttl` (10 to 100 seconds) plus `turn.ttl`, 60 to 3600, default 600; interpretation 49), the opaque id being FormLogic's keyed hash of the endpoint (interpretation 36). An entry never mixes `stun:` and `turn:` urls (the decoders treat any entry with a `turn:` url as TURN); at most 8 entries of at most 8 urls; `turnCredentialExpiresAt` is the earliest TURN `expiresAt` or `null`; `relayOnly` needs at least one TURN entry. Vector `A5` is the credential known answer.

**Aokie mailbox routes.** The party comes only from the verified admission: role `plugin` is `plugin`; a mobile is `mobile:<holderKeyThumbprint>`. Mailboxes are `app:<appId>@<dsk>/<party>`. Every request draws on a bucket of its admission (120, refilled 10 a second: `429 rate_limited`), re-reads the device row (`401 revoked` for a removed phone, a removed desktop or its removed phone; `403 forbidden` when the desktop's roster row no longer lists the phone; a desktop with no roster row has excluded nobody) and answers a bearer that is missing, forged, expired or of another kind with one `401 invalid_token` (20 a minute per address, then `429`). A bearer is good up to and including `exp` + 30 s. `GET /v1/aokie-companion/relay/challenge` returns `challenge.schema.json` (25 s lifetime; built only from the bearer; the plugin's peer set and the mobile's `expectedPeerKeyThumbprint` are mutually exclusive, and each omits the other's members entirely). `POST /v1/aokie-companion/relay/frames` `{"to":"plugin"|"mobile:<thumbprint>","frames":[...]}` (`compat-frames-request`): 1 to 64 frames, each a JSON object of at most `limits.lanes.sig.body` bytes once encoded (`413 relay_frame_too_large`); a mobile may address only `plugin` and the plugin only a phone (`403 relay_target_forbidden` otherwise); the plugin's post to a phone that its own admission does not list, whose device row is not active, that the roster does not list, or that belongs to another desktop is answered like a delivered post (`200`, the same members) and stores nothing (Interpretation 46); a frame is stored as decoded and encoded again, and is delivered with the relay's own record of its sender (interpretation 38); a mailbox holds 1,024 frames or 8 MiB, and the plugin's, to which every phone posts, gives no phone more than a quarter of either (`429 relay_backpressure`, all or none; interpretation 42); TTL 120 s; answer `{"accepted":N,"seq":N,"time":N}` (`compat-frames-accepted`). Facade reads do not acknowledge: `since` only selects where to read from (a valid `Last-Event-ID` header wins), and frames live until their TTL. `GET .../frames?since=&wait=` returns `compat-frames-page` (`frames`, `lastSeq`, `time`, and `hold` when a wait was asked for; at most 128 frames and 1 MiB, the first always returned; `lastSeq` is the last frame's `seq` or, with none, the cursor asked for; `wait` up to `min(20, wait.max)` is a core hold; interpretation 43). There is no consent filter: the plugin is the consent authority.

`GET /v1/aokie-companion/relay/stream`: SSE framing over a bounded poll that flushes at once. Verify the admission and the device row; register a core hold for the party (a newer stream or frames wait for the same party ends this one within 250 ms with an `end` event; `wait=0` holds nothing and supersedes nothing; at the hard limit the stream is `503 companion_unavailable` with `Retry-After: 2` and a frames wait is answered at once with `hold.refused`); `deadline = min(now + min(20, wait.max) s, admission exp + 30 s)`. Before any wait send status `200`, `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-store`, `X-Accel-Buffering: no`, and write `retry: 2000\n\n: connected\n\n` and flush. Then write each frame as `id: <seq>` / `event: frame` / `data: <compact JSON {"seq","from","subjectId","grants","frame"}>` (`compat-stream-frame`); after the first frame wait at most 50 ms more to coalesce a burst; every 2 s without output write `: keepalive\n\n`; exit at once when the client has gone, and within a step when the phone is removed. At the deadline, or when superseded, write `id: <cursor>\nevent: end\ndata: {}\n\n` and exit; `end` is never omitted, and nothing is written after the admission's own end. A relay advertises `compat.sse-framed-poll` only after a streaming probe passed on this host (or `compat.sse` is `force`).

## 11. Response shapes

1. Every dynamic JSON success body carries `"time"` (Unix seconds). `"v": 1` appears in poll, post results, presence, device list, device patch, revoke-all, roster, `ack`, pairing fetch, admin capacity and admin status responses. Static `info` carries neither. Error bodies carry no `time`. `204` responses have no body.
2. `GET /v1/health` is exactly `{"ok":true,"time":N,"authHeaderSeen":bool}`.
3. Poll: `hold` appears only when the request asked for `wait > 0`: `{"granted":true}`, `{"refused":true,"retryAfter":N}` or `{"granted":true,"superseded":true}` (with the header `X-OAIY-Hold: granted|refused`); `reset: true` appears only on a reset (and then `items` is empty and `more` false); `hdr` in a delivered item is always an object; `rp` is optional.
4. `POST /v1/devices/self/meta`: `200 {"v":1,"time":N}`. `POST /v1/devices/{id}` (patch): `200 {"v":1,"device":{...},"time":N}`. Revoke one: `204`. `POST /v1/devices/revoke {"role":"phone"}`: `200 {"v":1,"revoked":["dev-..."],"time":N}`. Token rotate: `200 {"token","graceUntil","time"}`. Enroll: `201 {"deviceId","token","relayId","time"}`. A device list entry is `{id, role, name, ver?, createdAt, lastSeen, revokedAt, thumbprint, ownerDesktop, grants, flags:{canCmd}, push:{kind}}`; members that do not apply are `null`.
5. `POST /v1/admin/capacity` takes `{"workers":int>=1,"streamOk":bool,"maxBody":int,"maxHold":int}` and answers `200 {"v":1,"effective":{"workers","heldSoft","heldHard","waitMax","streamOk","laneBodies":{lane:int}},"time"}`. `GET /v1/admin/status` answers `{"v":1,"version","php":{"version","sapi","extensions":[...]},"db":{"driver","sizeBytes"?},"items":{"live","bytes","oldestAgeS"},"devices":[{id,role,name,online}],"holds":{"soft","hard","measured","byKind":{...},"live"},"rejected24h":{code:n},"noAuthHeader24h":n,"tokensOlderThan90d":[ids],"warnings":[strings],"time"}` plus a `diag` object with `?diag=1`. Both schemas allow additional members.
6. The first relay serves the lanes `cmd`, `res`, `ctl` and `sync` (and `ring` when call features are on); `info.limits.lanes` lists only lanes actually served, and `features` lists only implemented features (initially `poll`, `items`, `presence`, `methods.post-forms`).
7. `Retry-After` is mirrored in `error.retryAfter` on 429 and 503 of the native routes. An error of the Aokie compatibility routes has exactly `error`, `code` and `message` (`compat-error.schema.json`): the wait is the header alone (interpretation 37).
8. The pairing routes: `POST /v1/pair` `201 {"pid","exp","time"}`; `GET /v1/pair/{pid}` `200 {"v":1,"state","offer","mac","exp","time"}` for `open` and `answered`, `{"v":1,"state":"approved","deviceId","sealedToken","receipt":{"issuedAt","signature","grants"},"time"}` for `approved`, `{"v":1,"state":"denied","time"}` for `denied`, plus `hold` when the request waited (as on a poll); `POST .../response` `202 {"state":"answered","time"}` (no `v`, as the design gives it); `POST .../decision` `200 {"v":1,"state","deviceId"?,"time"}`; `POST .../reject` and `.../burn` `200 {"v":1,"state","time"}`.
9. The compatibility routes (section 10.6): the admission answers are `admission-plugin-response` and `admission-mobile-response` (no `v`, no `time`, as the decoders are strict); `POST .../frames` answers `{"accepted","seq","time"}`, `GET .../frames` `{"frames","lastSeq","time"[,"hold"]}`, an SSE `frame` event carries one element of `frames`, and the challenge has no `time` (it has `expiresAt`). Their errors have three members.

## 12. Vectors and conformance

`vectors.json` holds, for each of Appendix A0 to A12 of the design, the inputs and the expected outputs: A0 the roster hash (anchor: the Aokie README), A1 a JWS EdDSA signature (anchor: RFC 8037 A.4), A2 a token, A3 pairing v3 (secret, typed code, `pid`, offer and MAC, response claims, signature and MAC, SAS, approval receipt), A4 an admission bearer (and A4b the bearer sizes for 1 to 64 phones), A5 a TURN credential, A6 an info proof (A6b over the full info document), A7 an enrolment key and proof, A8 a command container, A9 a ticket, A10 a rotation statement, A11 a ring signature, A12 the small-order X25519 encodings with their bit-255 variants. Extras: canonical JSON cases and refusals (including `-0`), token acceptance and refusal cases, thumbprints, typed-code and SAS check-character samples, `sasNegative` (the SAS of `A3` computed from the raw bytes of `pid` and the two wrong readings that take `pid` as text), the error taxonomy, the lane table, and external anchors (RFC 2202, 4231, 5869, 7748, 8032). All keys are fixed public test seeds.

Every deterministic value is recomputed three times: by `generate_vectors.py`, by `../../tests/relay_conformance.py` (Python, from the recorded inputs, without importing the generator) and by `verify_vectors.mjs` (Node). Sealed-box outputs are randomised by the ephemeral key and have no fixed vector here (the recorded pairing and Aokie fixtures under `fixtures/` are recordings, read by independent verifiers); PHP-sealed and Rust-sealed fixtures, and the composition of `A8` with a sealed box, belong to the desktop and pairing packages (`DK-04`, `RL-06`).

## Interpretations

Where the design is silent, ambiguous or wrong, this package makes the smallest sensible choice. An implementation follows these; the list is also what to raise with the design.

1. **`seq` starts at 1.** The design says "unsigned integer below 2^53" without a first value. Starting at 1 keeps `since = 0` (the default) meaning "nothing acknowledged" and makes `cursor = 0` mean "no item yet".
2. **Integer spellings.** JSON Schema's `integer` accepts `60.0`; the design says `ttl` must be an integer and rejects "fractional". The relay rejects any spelling with a fraction or exponent for integer members (`60.0`, `6e1`), consistent with the canonical form's "integers only". A schema cannot say this; the black-box suite must.
3. **HEAD is `405`.** The design allows exactly GET, POST, OPTIONS and the three aliases and says "anything else is 405".
4. **`hold` is present only when `wait > 0` was requested.** The design's example shows `hold` on a hold; for `wait=0` there is nothing to grant or refuse.
5. **Only `wait` is clamped.** `limit` and `maxBytes` outside their ranges, and a negative, fractional or non-numeric `since`, are `400 invalid_request`.
6. **Content type is required only when a body is present**; the charset parameter may be omitted.
7. **A provider's `deviceId` is its `prov-` id.** The design gives the enrol response as `dev-...` yet generates a `providerId` when a provider key is redeemed; the response member `deviceId` carries the `prov-` id for role `provider`.
8. **`401 revoked` needs the token row.** The design says a revoke "deletes its tokens" and also defines `401 revoked`; a deleted token could only be `unauthorized`. The relay marks the tokens revoked and keeps the rows, and answers `revoked` only after the secret verified, so nothing is disclosed to a party without the secret. A held poll of a revoked device ends with `401 revoked`.
9. **`GET /v1/items/{id}` requires both `to` and `lane`.** An id is unique only per (mailbox, lane, sender), and the sender is the caller; without `to` and `lane` the lookup is ambiguous.
10. **`hdr` may be absent on a post** (meaning `{}`); `to`, `lane`, `id` and `body` are required. The relay does not enforce a `ct` per lane.
11. **The 512 byte `hdr` cap is unreachable by the allow-list** (the largest expressible header is 405 bytes) but is still counted, in compact UTF-8 serialisation, as defence in depth.
12. **Base64url is read strictly**: a spelling whose unused low bits are not zero (for example the last character of a 43-character secret being `9` instead of `8`) is refused for tokens, nonces and every fixed-length key, so one secret has exactly one spelling. The design says only "characters outside the alphabet are rejected".
13. **`X-OAIY-Nonce`** is 16 to 32 bytes, i.e. 22 to 43 canonical base64url characters; anything else is `400 invalid_request`. The header name `X-OAIY-Proof` is used for two different proofs (a response header on `info`, a request header on `enroll`); the direction tells them apart.
14. **`limits.lanes` in `info` lists `ctl` too**, which the design's example omits, because a desktop may post it and its TTL bounds are then part of the contract. The `A6b` vector keeps the design's example verbatim.
15. **`Authorization` is `Bearer <credential>`** with the scheme matched case-insensitively and exactly one space; when the header arrives by more than one PHP source the first in the order `HTTP_AUTHORIZATION`, `REDIRECT_HTTP_AUTHORIZATION`, `getallheaders()` wins.
16. **Roster `revision` may be 0** at `POST /v1/roster` (a reinstall restarts at 0) while an admission needs 1 to 2^53-1.
17. **The design's Appendix A lists sealed-box fixtures "still to be produced by RL-01"; section 8.2 assigns them to `DK-04` and `RL-06`.** A randomised output cannot be a known answer, so `vectors.json` has none. `RL-06` records the PHP-sealed direction in `fixtures/sealed-token.json` (real relay output, opened by libsodium in PHP and, without libsodium, by two independent readers in Python and Node; see `fixtures/README.md`); the Rust-sealed direction, and the composition of `A8` with a sealed box, wait for the desktop code that can seal (`DK-04`, `DK-07`).
18. **The plugin bearer sizes of Appendix C (964 for one phone, +92 each) reproduce exactly** when the plugin subject id is `aokie` (vector `A4b`); another id changes the size by twice its length difference.
19. **`ring` is `403 feature_disabled` while call features are off**, and a ring with an invalid `hdr.sig` is `400 invalid_item`, not `403`.
20. **Timing of `Retry-After` values**: 1 second for the poll gap rule and lookup limit, 5 for `quota_exceeded`, 60 for `ip.authfail`, 2 for a refused hold, as the design's tables give them; other 429/503 answers use the bucket's refill time, rounded up.
21. **The SAS input carries the raw 16 bytes of `pid`, and in general raw bytes, never their text, enter hashes, MACs, signatures and key derivations.** The design writes `info = "oaiy/pairing/3/sas" || 0x00 || pid` and elsewhere calls `pid` a 22-character b64u string, so the prose reads naturally as the text: an independent implementation built that way got `24b574fd2e0d1e24` where the vector has `3563599914bdf7f9`, and nothing in the prose could tell it it was wrong. The generator, the design's own value (`6NHN-K68M-QQVZ-5`) and the vectors use the raw bytes (a 35-byte `info`). This package says so at every place where a value with a text spelling is an input to a hash or KDF (section 1, the `pid` row of section 2, the typed code, the SAS, secret storage, the slot ETag, the signed bytes of a container and of a rotation statement, the domain table), and `extras.sasNegative` records the two wrong readings, `pid` as its b64u text (41-byte `info`, `24b574fd2e0d1e24`) and as its hex text (51-byte `info`), with the value each produces, so that an implementation can show it does not make either. The one place `pid` is text is the approval receipt, because that is a JSON string.
22. **The item ids `.` and `..` are refused** (`400 invalid_item`, and in a `GET /v1/items/{id}` path `404 not_found`) although they match `[A-Za-z0-9._-]{1,128}`. An id becomes a path segment in a URL and is a name in stores that are files or paths, and `.` and `..` are the two names that a URL parser, a proxy or a file system resolve away instead of keeping. Every other name made of these characters, `...` and `a..b` included, is an ordinary id. `common#itemId` says so with a `not`.
23. **`-0` is not an integer.** JSON's grammar admits it and JSON Schema's `integer` accepts it, but it is a second spelling of `0`, and a value that has two spellings is one that two implementations can disagree about (a signed or hashed text would differ). A request member that must be an integer (`ttl`, `since`, `wait`, `limit`, `revision`, and every other one) and every canonical-JSON input is refused if it is written `-0`; `0` and negative integers are unaffected (Interpretation 2 is the same rule for `60.0` and `6e1`). The refusal is in `extras.canonical.refused` for canonical JSON.
24. **The idempotency key of an item is (mailbox, lane, sender, id), not (mailbox, lane, id).** The design keys it without the sender, so a second provider posting an id another provider had already used got `duplicate` with the first provider's `seq` (or `conflict`), could learn that the id was in use, and could claim ids ahead of the sender that meant to use them. An id is chosen by its sender and belongs to it; `GET /v1/items/{id}` already answers only about the caller's own items, and a `res` may answer a `cmd` when the recipient of the `res` is a device that posted a `cmd` of that id to the desktop. The relay's database moves to schema version 2 for it and migrates an older database on first use.
25. **`GET /v1/pair/{pid}?wait=&state=`.** The design names `wait` and `state=answered` but not their rules. `state` is the state the caller last saw (`open`, `answered`, `approved` or `denied`; anything else is `400`); a wait is held only for a live rendezvous that is still in that state (without `state`, in the state it is in now) and only while it is `open` or `answered`, so a wait for a change that already happened, on a finished rendezvous, or on an unknown pid returns at once. `wait` is a decimal integer (`400` otherwise), clamped to `info.wait.max` and to the rendezvous's remaining life. The answer is the state at that moment, with `hold` as on a poll: `{"granted":true}`, `{"granted":true,"superseded":true}` when a newer wait for the same pid took over, or `{"refused":true,"retryAfter":2}` (the smaller of 2 and `info.wait.fallbackS`, as on a poll) when the pool is nearly full (then at once, as a short poll). A wait pins a worker, so it is an edge hold counted once, by its pid; at most 4 per client address (`429 rate_limited` beyond, kept apart from the pool count so that four waits of one address are four workers, not one).
26. **The `pair` item ids.** The design gives the item id as the pid, but up to three responses can be accepted (after a reject) and `(mailbox, lane, sender, id)` is unique (Interpretation 24; the sender of a `pair` item is `relay`). The first response's item is `<pid>`, the second's `<pid>.2`, the third's `<pid>.3`, so a redelivery is recognised and none is lost as a duplicate.
27. **Reject and burn.** A reject applies to an `answered` rendezvous (`409` otherwise) and clears the stored response; the third reject ends it (`expired`), so "fewer than 3 rejects have happened" means the first two reopen it. A burn ends any live rendezvous except an approved one (`409`: the phone has yet to read its token); burning one already ended is `200`. Denying is possible only for an `answered` rendezvous (`409` on an `open` one: use burn to end it early).
28. **`404` for the phone, `410` for the owner.** The phone's two routes answer an unknown, an expired and a burned pid with one `404` produced by one lookup, and judge the request body first, so nothing about a bad request tells a stranger whether a pid exists. The desktop's three routes answer another desktop's pid exactly like an unknown one (`404`) and its own ended rendezvous `410 expired`.
29. **What the relay checks at `POST /v1/pair`.** The offer must be a JSON object; beyond `appId` and the thumbprint it must name the calling desktop as `desktopConnectionId`, and its `desktopEndpointKey.publicKey` must be a valid Ed25519 key of no small order whose thumbprint is the one given (`422` for a key, `400` for a mismatch): the relay later verifies the approval receipt against that key. A desktop may have 16 rendezvous open at once (`429 quota_exceeded`, `Retry-After: 5`); a pid that exists is `409 conflict` (an ended one the collector has not reached does not count). `ttl` is an integer from 1 to 900, default 600.
30. **What the relay checks of the phone's response.** It cannot check the MAC (it never has `mac_key`) or the signature (the key is inside the claims and unproven), so it stores the text as sent; the text must be a JSON object of `kind` `aokie_mobile_pairing_response` (`400`), which keeps other junk out of the desktop's inbox. The pair item is committed in the same transaction as the state change.
31. **What the relay checks of the approval** (each a `422`, defence in depth: the desktop and the phone still verify). The keys named in the approval are the keys in the response the phone posted (`claims.mobileEndpointKey`, `claims.mobileX25519`) and the thumbprint is the Ed25519 key's; the X25519 and Ed25519 keys are not of small order; `appId` is the rendezvous's; and the receipt verifies under the desktop endpoint key of the offer over the canonical document (grants sorted by the relay before it checks, so their order in the request is free). An approval that fails changes nothing.
32. **Grants** in an approval are among the fourteen names of the Aokie protocol (`state_read`, `caller_read`, `captions_read`, `assistance_read`, `assistance_respond`, `monitor`, `consult`, `takeover`, `resume_aokie`, `end_caller`, `rtc_signal`, `participants_read`, `participant_identity_read`, `audio_levels_read`); another name is `422`, because the phone's decoder refuses an admission that carries one. The relay does not require `state_read` at the approval; the admission does (section 10.6).
33. **Phones per desktop and re-pairing.** At most `limits.rosterMax` (16) phones are active for one desktop and app; the 17th approval is `409 conflict`. A phone that pairs again with the same Ed25519 key replaces its old device: the old device is revoked once the new one exists, so it is not counted twice and its old token stops working. Two approvals at the same moment are counted one after the other (the second counts what the first made), so the 17th phone is refused and a key never has two active devices; an approval for a desktop that was revoked meanwhile is `401 revoked` and makes nothing.
34. **The sealed token** is `sodium_crypto_box_seal` of the 63 character device token; the relay keeps only the token's hash, and the sealed box is deleted with the rendezvous ten minutes after the phone read a terminal state (or at expiry).
35. **`ip.pair` counts the phone's two routes** (`GET` and the response), not the desktop's three: those are authenticated and counted per token.
36. **The TURN username carries FormLogic's opaque id, not the subject id.** Section 10.6 and Appendix A5 write `username = <expiry>:<subjectId>`. A device id in the username is visible in clear text in every STUN request and in every coturn log line, which is a third party's. FormLogic, whose credentials the plugin and the phone already receive, uses `<expiry>:` and the first 32 hex characters of `HMAC-SHA256(secret, "aokie-turn-id" || 0x00 || role || 0x00 || appId || 0x00 || subjectId)`. The relay uses that construction byte for byte (FormLogic's own unit-test answers are tests of the relay: its ids `b76588ed...` and `9ad5b440...` and both minted admissions), so a coturn shared by the two sees the same id for the same endpoint. `coturn` accepts any text after the colon; the schema pattern is unchanged; `A5` remains the known answer for the credential (an HMAC over a username of any content).
37. **An error of the compatibility routes has exactly three members.** The design gives FormLogic's shape `{"error":true,"code","message"}` for the routes under `/v1/aokie-companion/`; the native shape's `retryAfter` is not added to it, because the phone's error decoder (`MobileApiError`) is `deny_unknown_fields` and would fall back to a bare status, losing the code and message, on the very 429 and 503 that carry a wait. The wait is the `Retry-After` header. The shape is chosen by the path, so it also covers what fails before a handler runs (a body of another type, an unsupported level, a 404 or 405, an unexpected 500) and the alias `POST /v1/aokie-companion/admission`.
38. **Frames.** A frame is a JSON object; `frames` is a list of 1 to 64 objects and the request an object whose other members are ignored. The relay records who posted a frame (the party, the admission subject and its scopes, filtered to the fourteen names) at the moment it verifies the bearer, and every read returns that record next to the frame: a `from`, `subjectId` or `grants` inside a frame are the frame's own members and carry no authority (the plugin's `subjectId` is its plugin id). A frame is decoded without associative arrays and encoded again without escaping slashes, with every non-ASCII character written as `\uXXXX` (a surrogate pair above the BMP; Interpretation 52), and floats in their shortest form (whatever the host's `serialize_precision` is), so `{}` stays an object, integers up to 2^63 - 1 stay integers, `1.0` stays `1.0`, and key order is kept; an integer past 64 bits would become a float and lose digits, so the request is `400`, and so is a bare `-0` (Interpretation 23: PHP reads it as the integer 0, so it would come back as `0`; `-0.0`, `-0.5` and the text `"-0"` are ordinary). The checks run in this order: bearer and gate, JSON body, `to`, direction (`403`), the frames list, each frame (`400` or `413`), then the quotas (`429`). Revoking a phone retires the frames it had already posted to the plugin, as it retires what a device posted to any inbox (they carry the party, not the device id, so the relay finds them by party in the desktop's plugin mailbox), and deletes the phone's own mailbox.
39. **Times.** A bearer (TTL 90 s) is verified through `exp` + 30 s inclusive, by every route and by the end of a held wait or stream (nothing is emitted after that second). The challenge lives 25 s. Frames live 120 s (`lanes.sig.ttl`).
40. **Which carrier an admission advertises.** `relay` in `supportedTransports` is the framed stream. It is offered when call features are on, `compat.sse` is not `off`, and the host's streaming probe passed (`auto` and `on`) or `compat.sse` is `force`; `relay-poll` is offered as `relay.mode: "poll"` whatever the probe says; a list with neither is `422`. The shipped phone sends `["relay"]` only and the desktop's broker sends no `supportedTransports` for the plugin at all (`upstream.rs`), which is read as `["relay"]` (design 4.14.2 says a request "may carry" it; a first version answered `400`, and then no shipped desktop could get a plugin admission); both ignore `relay.mode`, so on a host that does not flush they get `422`, which is right: there is no framed stream for them to open.
41. **Mobile admission.** The phone must be the token's own device (`deviceId`, key thumbprint, app), paired to a desktop that is not removed (`403` otherwise), listed by that desktop's roster row for the app when there is one, with a recorded `peer_thumbprint` (its pin, from the pairing) that is not its own key, and with `state_read` among grants the phone's decoder knows. Unknown names are dropped: the phone refuses an admission that carries one.
42. **Mailbox limits.** `limits.sigItems` (1,024, at most 1,024) frames and `limits.mailboxBytes` per party mailbox; `limits.sigSenderShare` (a quarter) of either for one sender, applied only to a mailbox that several parties post to (the plugin's), not to a phone's, which only the plugin posts to: a call's eight frames a second would otherwise overflow it in 32 seconds. A batch is stored whole or not at all. Expired frames are swept from a mailbox when it would otherwise overflow.
43. **Waits.** `wait` on a frames read and the stream both last at most `min(20, wait.max)` seconds (at least 1) and never beyond the bearer's end; both are the same core hold kind (`stream`), one per (desktop, app, party), so a newer one ends the older. `wait=0` holds nothing and supersedes nothing (the plugin's tail priming must not end its own stream). A refused wait is `200` with `hold: {refused, retryAfter}` and the header `X-OAIY-Hold: refused`; a refused stream is `503 companion_unavailable`.
44. **`gatewayUrl` is never dialled.** It is `public_url` with its scheme replaced by `ws`/`wss` and `/v2/realtime` appended, because both decoders parse it and refuse anything but `wss`. With an `http` public URL (development on loopback) the answers carry `ws://` and `http://` and the decoders refuse them; the status page says `public_url is not https`.
45. **`dsk` in the claims.** The device id of the desktop the party belongs to, read only by the relay; the Aokie decoders never parse the bearer (`AdmissionClaims` is `deny_unknown_fields` but is not used by the plugin or the phone), so the extra member is safe there and is what keeps two desktops of one relay with one app id apart.
46. **The plugin's post to a phone that is gone is a success.** The design has the plugin address a phone its admission lists whose device is active (`403 relay_target_forbidden` otherwise). The shipped plugin maps a 403, 404 or 503 from the frames route to a re-bootstrap of the whole relay carrier and returns the first error of a broadcast, so after the desktop revokes or drops one phone the plugin's next `assistance_request` or `plugin_idle` to the phones would end the session of every phone, which design 6.7 says must not happen ("revoke during a live call: the relay cuts the phone off at once; the plugin keeps going"). The relay therefore answers a post to a phone that is revoked, out of the roster, not in the plugin's admission, or another desktop's exactly like a delivered post (`200`, `{"accepted":N,"seq":N,"time":N}`, the sequence number the last frame would have had) and stores nothing, after the same checks of the frames themselves (`400`, `413`) so that the answer does not tell a good frame from a bad one differently. The `403` stays for a target that cannot be right at all: a phone addressing anything but `plugin`, the plugin addressing `plugin`. A dropped post is not counted against any mailbox; the phone itself is refused (`401 revoked`, `403`) at its own next request. **A dropped post and a delivered one are not indistinguishable**, and only the owner's own plugin can see how: the `seq` of a delivered post is the number its frames were stored with, and the next delivered post continues from it, where a dropped one stored nothing and a later answer repeats the number; a delivered post can be refused `429 relay_backpressure` by a phone mailbox that is full, a dropped one never is; and a dropped one answers a little faster (no mailbox is read or written). The plugin learns by those means only that a phone it addressed is gone, which its roster and its admission already told it; no phone and no other desktop can ask the question, and the answer to a stranger is the `403` of an address that is not in the admission. The relay does not hide it further because hiding it would cost a write for every dropped post.
47. **A display name is at most 60 code points and at most 120 bytes.** The relay cleaned names to 60 characters and put the stored one into `device.displayName` of a phone's admission, but the shipped phone refuses an admission whose display name is longer than 120 bytes (`managed_auth.rs`), and 50 CJK characters are 150 bytes and 35 emoji 140: such a phone would be admitted (`200`) and then never connect. A name is now cut between code points to 120 bytes when it is stored (pairing, enrolment, a rename) and again when the admission is built, so a name stored before the cap still fits. A cut may leave a base without its combining marks or a joiner at the end; the shipped phone checks the length only.
48. **A phone's frames assert at most what the desktop grants it now.** The scopes recorded with a frame are the bearer's, intersected with the device row's current grants (the row is read on every request anyway), so a grant the desktop takes away (a phone cut from `takeover` and `monitor` to `state_read`) is no longer asserted at the phone's next post instead of for the rest of the 90 seconds of its bearer, and a grant the bearer never had is never added when the desktop widens the row. The bearer itself is not changed, and the next admission carries the new grants. A phone left without `state_read` keeps posting until its bearer ends: the admission is where that is refused.
49. **The expiry of a TURN credential is rounded down to a window.** Design 4.14.3 gives `exp = now + turn.ttl`. coturn keeps its `user-quota` per username exactly as it receives it, and the username holds the expiry, so an endpoint that mints an admission every 50 seconds (a plugin and a phone each do) or up to 30 times a minute (the mint limit) would have a new quota key with every mint and no quota at all. The expiry is now the start of a window plus `turn.ttl`, the window being a sixth of `turn.ttl` clamped to 10 to 100 seconds (100 for the default 600). An endpoint's admissions inside a window carry the same username and credential; a credential is always more than five sixths of its lifetime ahead (never below 50 seconds, above the decoders' 30) and never past `turn.ttl`. FormLogic's known answers (its `now` is a multiple of 100) are unchanged.
50. **The 60 GETs of a rendezvous are for its open and answered states.** Section 4.10.6 gives a rendezvous 60 GETs in its life. Counting a read of an outcome (approved, denied) as well let anyone who learned the pid spend the budget the phone needed to read its own result: after the token was made and the roster place used, the 61st GET was `429` for the rest of the rendezvous's life (30 a minute from one address is enough, and a phone that short-polls at 2, 4 and then 5 seconds after a refused hold reaches 60 in 300 seconds). Only reads of a rendezvous that is open or answered are counted against the 60; a read of an outcome is answered without counting, and bounded by a bucket of 10 a minute per client address and pid (`429 rate_limited`, `Retry-After`), on top of `ip.pair`. A rendezvous that has ended (burned, expired) is the phone's `404` as before. The budget of an open or answered rendezvous is unchanged, and a phone whose budget ran out while it waited can still read the outcome once there is one.
51. **A retry of a request whose answer was lost is answered as the first was.** The design answers `409` to a `POST /v1/pair` for a pid that exists and to a second response, so a desktop or phone whose `201` or `202` was lost on the way and which retried (both do) was told that somebody else had taken the pid or answered, an alarm that is false and that a phone shows the owner as such. An identical request is now recognised as the same one: the desktop's `POST /v1/pair` with the same offer, MAC, app and thumbprint for a live rendezvous of the same desktop gets `201` with the original `pid` and expiry (a `ttl` that differs is ignored, the rendezvous is the one that was made, and the retry is not counted again against the 16 that may be open); the phone's response whose text is the one the rendezvous accepted last gets `202 {"state":"answered"}` again and nothing is written, while it is answered and after the owner has decided (the relay compares with the stored text, or with the hash its `pair` item keeps for ten minutes; once that is forgotten a retry is `409` as before). A different offer, MAC, app, desktop or response text stays `409`, and a response that a reject discarded is a new response into the open rendezvous, with its own item.
52. **Frames are stored and delivered in ASCII.** Design 4.14.4 has the relay re-encode a frame with `JSON_UNESCAPED_UNICODE`, exactly as FormLogic does. The shipped plugin reads a stream in network chunks and decodes each chunk on its own with `String::from_utf8_lossy`, so a chunk boundary that falls inside a character turns it into U+FFFD: one of 835 byte offsets in a recorded stream in four places corrupted "héllo". The relay now writes every non-ASCII character of a frame as `\uXXXX` (a surrogate pair above the BMP) when it stores it, and every stream event and frames page carries that text, so a chunk of it cannot be split. A reader that decodes JSON gets the same characters (the plugin and phone read the frame into a value and write it again); a reader that compares text is the only one to see a difference. The cap of `limits.lanes.sig.body` still counts the frame as it was sent (raw UTF-8, as the design and FormLogic count it), not as it is stored, which is up to twice as long for text in the BMP above U+07FF and three times for a character outside it. The recorded streams are ASCII and the fixtures verifier cuts them at every byte offset, decoding each chunk lossily as the plugin does, and shows with a control that a raw-UTF-8 stream is corrupted by some offset.
53. **One party's streams and frames waits are bounded before anything else is done.** Design 4.7.2 gives a party (the plugin, or one phone) one hold at a time: a newer stream or frames wait supersedes the older, which ends within 250 ms. But a superseded hold still pins a worker until it notices, every request that reaches the relay costs a worker whatever it is refused for, and the only bound on a bearer's requests was its own bucket (120 at once, 10 a second), of which a party has a new one with every admission it mints (30 a minute). Fifty streams at once from one bearer therefore kept a five-worker pool busy for over two seconds (a health check took 2.67 s; design 9.2 asks for under a second), and 100 streams every two seconds with a new admission each time did it for as long as they lasted. Two bounds are now applied to a stream open or a frames wait, from the verified bearer alone and before the request does any database work of its own (a refusal costs a read of one folder and of the one row of the party's open bucket, and writes nothing): at most 3 of a party running at once, the ones being superseded included (`Holds::STREAM_INFLIGHT_MAX`), and a bucket of 20 opens for the party, refilled three a second, whichever admissions it holds (`Holds::OPEN_BUCKET`, `OPEN_REFILL_PER_S`; 10 and one a second in the first version, see the end of this paragraph). A refusal is `429 rate_limited` with `Retry-After` (the shipped carriers read a 429 as a failure to retry; they map 403, 404 and 503 to a re-bootstrap and a 429 to neither). During its first two seconds a hold looks for a newer one every 50 ms instead of 200, so a hold that is superseded (the newest are) pins a worker for a quarter of the time. Measured through a pool of W workers: fifty streams at once from one bearer, health at worst 0.3 s on 5 workers, 0.2 to 1.0 s on 8 and 0.2 s on 20, where it was 2.67 s, 1.34 s and under a second before; 100 streams every two seconds with a new admission each time, 0.7 to 1.0 s at worst. An honest carrier that opens one stream at a time and reopens when it ends stays far inside both bounds. **A carrier that cancels opens is a different case, and the first sizing did not take it into account.** A select-driven carrier drops an open that has had no answer for a while (the host's queue is full) and opens another at once; the dropped requests are still in the queue, are served when a worker comes free, and each draws on the bucket and the in-flight count before it finds nobody to answer. Measured with a model of that carrier (the review's, `t36`: open, cancel after 40 to 150 ms without an answer, reopen at once, a five-worker pool kept full by 8 second holds for 50 seconds) the carrier saw one `429` in a run and never two in a row, with the first bucket and with a bigger one alike: the long gaps between its successful opens (26 s) are the saturated pool, which no bound of the relay changes. The review's runs with the carrier's own decoders saw more refusals of the live open (the bucket empty because abandoned opens had drawn on it) and, small samples, more failed sessions than before the bound. The carriers pause one second after a failed open, ignore `Retry-After`, and give a session up after three failures in a row; so the refill is now three a second (the bucket 20) and not the one a second that their own pause would take back: a retry one second after a refusal finds a token even when one other open drew on that second (a test). **This is reasoned, not measured with the real decoders**: the model above showed no difference between the two bucket sizes (one refusal in a run either way), the review's own runs had too few sessions to say, and the claim is only that the bucket is not the thing that fails a carrier when a few opens draw on it while it pauses; a flood of abandoned opens that drains it (dozens, served together once a saturated host frees its workers) can still be three refusals in a row for a carrier, and no size of bucket that still bounds a party's rate prevents that. What a party that keeps inside the bucket may do is about 3 opens a second at most, a seventh of a worker at the 50 ms an open costs; fifty at once from one bearer still leave health at 0.14 s at worst on 5 workers, 0.05 s on 8 and 0.04 s on 20 (the review's `t5` run), a burst of ten opens a second for fourteen seconds (an abusive carrier) is let through 61 times in 140 and costs the others nothing (0.04 s worst on 5, 0.32 s on 8). Not done: answering an open over the bucket with a stream that ends at once instead of a `429` (the carriers would reopen at once, a tight loop that costs a worker each time), or after a wait (which pins the worker the bound exists to save).
54. **A client that hangs up is found by the stream in about two seconds, and by a frames wait not before its end.** Design 4.14.5 relies on the keepalive write to find a client that has gone ("about 2 s"). PHP learns that only when a write fails, and the first write to a connection whose peer has closed succeeds (the reset comes back afterwards), so a keepalive every two seconds found it on the second, at about four (4.1 s measured on `php -S`), and an abandoned stream pinned its worker that long. A second write, an empty comment (`:` and a blank line, no event) a quarter second after each keepalive, finds it after about two and a quarter; the recorded idle stream shows both. A frames wait is a JSON answer with its status and headers still to be decided (a revocation ends it with 401), so it cannot write a byte before it ends and, on `php -S`, PHP-FPM and any host that reports an abort only on a write, an abandoned one pins its worker until its own end (at most 20 seconds); a call to `flush()` to try would commit the headers early (it did, and the answer went out as `text/html`; a test now shows the headers are the ones meant). What bounds it is Interpretation 53: a newer wait or stream of the party ends it within a step, at most three of a party run at once, and a bucket bounds how often a party may open one. A host whose server tells PHP about an abort without a write (an Apache module) needs nothing more; the shipped carriers open the stream, not a wait.
55. **A post checks its sender and its recipient again inside its own transaction.** The design has a revocation stop what a device has posted and what is posted to it (4.5). The relay authenticated the sender and authorised the post (the recipient's row) before the post's transaction, so a post that was in flight when the device was revoked could commit after the revocation returned: eight parallel posters through a phone's revoke left one to three live items after it in 7 of 8 rounds on SQLite and in 13 of 15 on MySQL, and a post to a device that was being revoked made its mailbox again (20 of 20 rounds on MySQL). The post now asks again, first thing inside its transaction and before its mailbox is made or read, whether its sender and its recipient are there and not revoked (`Mailbox::requireActive`): a revoked sender is `401 revoked`, the answer its next request would get, and the whole request when it is a batch; a revoked or missing recipient is the `404 not_found` the ACL gives, item by item. On MySQL and MariaDB the check takes a shared lock (`LOCK IN SHARE MODE`) on the device's row and a revocation takes the same row exclusively before it retires anything, so a post already past the check finishes before the revocation goes on and one that comes after it finds the device revoked; SQLite's write lock covers the file. The Aokie frames do the same for their sender (the phone, and the desktop it answers to; for the plugin the desktop that brokered it: `401 revoked`) and for the plugin's recipient phone (revoked, or out of the roster: the post is dropped and answered as delivered, Interpretation 46, and no mailbox is made for it); the phone's response to a rendezvous whose desktop was revoked is the `404` of an unknown pid and files nothing. What the transaction does not check is the roster's list for a sender: a phone the roster no longer lists is revoked by the same push.
56. **A roster push is one transaction, one at a time per desktop.** Section 4.5's push stores the desktop's list and revokes the phones it no longer lists. The relay stored the list in one transaction and revoked the phones in others, so two pushes at once each stored a list and each revoked what the other's list kept (two simultaneous pushes with different lists left both phones revoked and the stored roster naming one of them in 40 of 40 rounds: it fails safe, but a desktop never meant it), a failure halfway left the new list stored with the old phones active, and a reader could see either. The push now takes the desktop's gate (the gate an approval takes, so a push and an approval do not interleave either), stores the list, and revokes the phones it drops inside the same transaction; the held requests of the dropped phones are told after the commit. Two pushes at once are applied one after the other, each whole, and a revocation is still final: a phone dropped by the first is not brought back by a second that lists it again (the stored roster may then name a revoked phone, as it does when the two pushes come one after the other).

57. **A consumer de-duplicates on (from, id), after authenticating the sender.** With the sender in the idempotency key (Interpretation 24) two senders' items of the same `id` to one mailbox and lane are two items, and both are delivered, each with the `from` the relay names and the `seq` it was given. A consumer that keeps a record of the ids it has seen (the desktop's replay cache, a phone that reconnects after a lost acknowledgement, a provider matching a `res` to a `cmd`) keys it on the pair: on the `id` alone one sender could make another's item look like a replay, and so make a consumer drop it, by choosing the same `id`. The relay's own rule is unchanged (a repeat by the same sender is `duplicate`, a repeat with another body `conflict`), and a sender still chooses its ids (`cmd-<uuid>`, `res-<command id>`) so that an honest pair never meets. For a signed command the pair is the provider's pinned key thumbprint and the `id` inside the signed bytes, checked after the signature (section 10.3, step 7).
58. **At most three polls that wait, of one credential, run at once, and the fourth is refused before anything is read: a bound in depth, whose benefit with the shipped gap rule is small.** Design 4.7.2 rule 5 and threat A12 say that one credential cannot pin more than two workers; Interpretation 53 bounded the streams and frames waits of a party and left the native poll, the hold every phone and desktop opens, as it was: one hold at a time that a newer poll supersedes, with the older still running for up to a step (200 ms; the protocol's bound for it is 250 ms, section 5.1.1) and the hold taken after the database had been read. The poll now takes its place in the registry first, before it reads or writes anything of its own (a refusal costs the credential's own check, which is a database read and comes first, and the read of one folder), by the same create-then-count call as the streams, so that a burst arriving in one instant cannot all pass a count that was made before any of them had a marker (the price is that each may count the others, so a burst is refused beyond the surplus: the review measured four at once refusing two and five refusing four, and the test of eight at once allows all eight to be refused, which is what section 5.1 says to a client); at most `Holds::POLL_INFLIGHT_MAX` (3) of a credential run at once, the ones being superseded included, and the fourth is `429 rate_limited`, `Retry-After: 1`, `error.rule: "in_flight"` (the gap rule's refusal says `"gap"`: section 5.1.1), writing nothing (no presence, no generation, no marker). A "credential" here is the device: the count is of the device's id, so every bearer a device holds counts together. A poll that does not wait (`wait=0`) and a lookup (its own hold kind, four at a time) are not counted: a `wait=0` poll holds no worker beyond its own few milliseconds. **What it is worth, measured, and what this text said before.** The figures first given here (health 6.8 s at the median and 10.3 s at the worst before the bound, 0.016 s and 0.23 s after) were measured on a relay whose `wait.gap_ms` was 0, which the tests set and the product does not ship (it ships 250; the option takes 0 to 5000), and the "after" figures did not reproduce. The gap rule (section 5.1) already answers `429` to a poll that follows an empty one within `wait.gap_ms`, and in a burst the first polls that are superseded end within a step and make most of the rest of the burst a gap-rule `429` at the price of one read. Measured again with the pool emulator (W `php -S` servers behind a front that queues, as PHP-FPM's accept queue does; PHP 8.4 on Windows; 50 polls at once from one phone token, six times 0.6 s apart, `GET /v1/health` every 150 ms meanwhile; W = 5, three runs of each unless said): with the shipped gap (250 ms) before the bound (`a99a1061`) health took 0.017 to 0.028 s at the median and 0.21 to 0.26 s at the worst, with the bound 0.019 to 0.028 s and 0.08 to 0.15 s (8 workers: 0.19 s before, 0.04 s after; 20 workers: 0.21 s and 0.05 s; one run each), and of the 300 polls 275 were refused by the gap rule before the bound and 288 after it. With `wait.gap_ms` 0, before the bound the median was 7.0 and 7.5 s and the worst 9.9 and 10.3 s (43 and 44 of 48 probes took over a second, two runs), with it 0.027 s and 0.10 s. One token polling back to back 25 times a second for nine seconds: with the shipped gap 0.022 to 0.030 s at the median and 0.06 to 0.09 s at the worst before, 0.024 to 0.028 s and 0.04 to 0.05 s after; with gap 0, 0.46 s and 0.85 s before, 0.022 s and 0.04 s after. The independent reviewer's runs of the same shape on a busier machine: gap 0, 11.3 s median and 14.5 s worst before, 0.051 s and 0.79 s after; shipped gap, 0.054 s and 1.05 s before, 0.047 s and 0.76 s after. A second review of the tree that has the bound measured, at the shipped gap, 0.05 to 0.06 s at the median and 0.65 to 0.93 s at the worst, against 0.019 to 0.028 s and 0.08 to 0.15 s here: the figures depend on the machine and on what else it is running, neither set is a promise, and what the tests require is health under a second at the 90th percentile and under two seconds at the worst, which both machines meet. The bound is therefore defence in depth: with the shipped gap rule its benefit is small (the worst health check took about half as long on a quiet machine and about a quarter less on the reviewer's), and with `wait.gap_ms` at 0, or where a burst gets past the rule because no poll of it has ended yet, it is the difference between a pool busy for ten seconds and one that is not. The pool tests of poll bursts (`tests/cases/pool.php`) run with both: gap 0, where the bound alone protects the pool, and the shipped 250. A `wait=0` burst of the same size (50 at once, six times, one token) left health at 0.02 to 0.03 s at the median and 0.04 to 0.10 s at the worst with the shipped gap or with 0, before the bound and after it, which is why those polls are not counted. No open-rate bucket was needed for polls, and none is added: the native pollers are not yet written, and a bucket that refuses opens is a failure to a client that does not honour `Retry-After` (a 429 on a poll is not one for a client that does, which section 5.1.1 requires of DK-03 and MOB-21a in rules a client can be built from and tested against). An honest client, with one poll in flight and a second only for the instant between a retry and the end of the poll it replaces, never meets the bound.
59. **A database that is busy, locked or gone for a moment is `503 unavailable` with a `Retry-After` on the ordinary routes and the `500 internal` that the shipped plugin retries on the compatibility routes, and never a `401` or a `404`; and the relay can say where and why it decided an error.** `Db::write` already answered `503` after three busy tries, but a statement outside a write transaction (the credential's own lookup, the limiter's counters, a poll's reads) that met a locked database, a deadlock, a lock wait timeout, a dropped connection or "too many connections" threw to the front controller and was a `500 internal`, which a client may treat as a reason to give up. Those errors (`Db::isTransient`: the busy codes, and MySQL's gone away, lost connection, too many connections, shutdown and user limit, and SQLite's I/O error, full disk and file that cannot be opened) are now `503 unavailable` on the ordinary routes, with `Retry-After: 1` (`5` when the database cannot be opened at all), logged as `db_unavailable` with the driver's code and the line; every other database error (a table that is gone) stays `500 internal`. **On the compatibility routes (`/v1/aokie-companion/`) every one of these failures is the `500 internal` in the Aokie shape, with no `Retry-After`, because that is the status the shipped plugin handles:** a statement that failed, a connection that is gone, a write that gave up after its three tries, and a database that cannot be opened at all. Before this branch the first two were already a `500` here; a write that gave up was a `503` here as everywhere (`Db::write` raised it), and a database that could not be opened was a `503` with `Retry-After: 5` in the native shape. **Both of those are changed on purpose, to the `500`**, because a `503` on these routes is the plugin's re-bootstrap and the closing of every live call, and a database that is busy or cannot be opened for a moment is no more a reason for that than a connection that dropped is. (The first fix of this finding left the write that gave up as a `503` on these routes, because the compatibility handlers' own wrapper answered the error before the front controller could change its status. The review found it on five of the eight requests (challenge, tail, frames post, frames wait and stream open); run against that tree with a competing writer that blocks every write, as the test now does, it is all eight, on SQLite and on MySQL. The wrapper answers nothing now, the front controller answers every error of these paths, and a test makes each of the eight requests meet a competing writer, a lost connection and a database that cannot be opened. The message of `12582837` and this text said that all of these were the `500` they had been, which was not so for the write that gave up.) The plugin reads a `500` as a failure to reconnect (`relay_status_error`, `companion_relay.rs` 1093-1108) and its frames post retries it three times, 250 ms apart (`post_frames`, 1025-1031), so a blink of the database is absorbed; a `503` is "unavailable for this app", a re-bootstrap (1101-1105), the post is not retried, the error leaves the channel and `gateway_worker` closes every live call with `fail_closed_all("gateway_disconnected")` (`errors.rs` 170-180). The phone retries any status three times (`post_batch`, `apps/aokie-mobile/.../companion_relay.rs` 647-700) and is not affected either way. **What a long wait does to that, in numbers.** A write that cannot get its lock waits `busy_timeout` (5000 ms on SQLite) or `innodb_lock_wait_timeout` (5 s on MySQL and MariaDB, which the relay's own connection sets) for each of three attempts, so a request gives up after about 15 seconds (a table or metadata lock is governed by another setting, `lock_wait_timeout`, which the relay does not set and which is a year in MySQL and a day in MariaDB by default; the relay takes no table lock, but a lock that another session holds on a table, during a migration or by hand, is waited for that long) (as it did before this branch), and the plugin cuts a challenge, a tail and a frames post at 10 seconds (`CHALLENGE_TIMEOUT` and `POST_TIMEOUT`, `companion_relay.rs` 38 and 40, used at 343, 516 and 995) and the opening of a stream at 10 seconds (`STREAM_OPEN_TIMEOUT`, 46): a request that is blocked by a lock that lasts longer than that is cut by the plugin as a timed out request, a transport failure that is the same "reconnect" and is retried the same way, before the relay's `500` arrives, and the relay's request goes on and may still commit after the plugin has given up on it (a frames post is then stored twice when the plugin retries it: the duplicate below). The `500` is what the plugin sees when the lock is shorter than 10 seconds, which a blink of the database is. Nothing here shortens the wait, which is not worse than it was; an answer within the plugin's 10 seconds for every lock would need every write path to give up in under that, and that is not done. The plugin's table of what each status does, with those lines, is `tests/lib/AokiePlugin.php`, and the tests of this paragraph hold the relay's answer on each of the eight requests that the plugin and the phone make (challenge, tail, frames post and stream open of the plugin; challenge, frames post, frames wait and stream open of the phone) to it, for a lost connection, a competing writer and a database that cannot be opened; a database that cannot be opened (before any route is known to the relay) is answered by the front controller in the shape of the route it was asked for. **A frames post that committed and then met an error is posted again by the plugin's retry, and its frames are stored twice** (a frames post carries no id by which the relay could recognise a retry, so the second post stores a second set of frames under new `seq` numbers, and a reader sees them twice): that is how it was before, and it is not hidden behind a `503`; whether the receiving side tolerates a frame that arrives twice is for the plugin and the phone, and the relay does not claim it. Reading every path from a database error to a status found none that makes a `401` or a `404`: a credential that cannot be looked up is an exception, not an absent row. Two failures that a review saw once each under heavy load on MySQL and could not reproduce in 78 reruns (a valid desktop token answered `401`; two of eight racing responders answered `404`), and that a second review could not reproduce in 920 runs, are therefore not explained by the relay's handling of database errors, and are not explained at all yet. What is added so that the next one is: `debug.error_sites` (off by default; the tests turn it on) logs, for every `401`, `404` and `5xx` answered, one line with the route, status and code, the file and line that decided it, **a reason code that tells the causes apart that share a line** (an unknown token id, a wrong secret, a malformed or missing bearer and a locked token are all `Auth.php`'s refusal; an unknown, an expired and a burned pid are all the same `404`), the relay's clock and the host's **as they were when the decision was made**, and the process, and no credential, id, header or body; a test that fails on a status it did not expect prints the relay's own record (`Relay::errorSites()`). One mechanism was closed that could have produced the `404`: the test clock, a file the relay reads for the time, fell back to the host's own time when a read of it failed, and the host's time is ahead of the tests', which keep a fixed date (the tests' clock starts at 1790000000, 21 September 2026, and the gap only grows: ten days when this was written), so that a 15 minute rendezvous is long over (`404`); it is read again, and an unreadable one is an error.
60. **The approval receipt the phone reads carries the grants it was signed over.** The desktop signs `Ed25519(desktopEndpointKey, "oaiy/pairing/3/approval" || 0x00 || canonical({"appId","grants" (sorted),"issuedAt","phoneThumbprint","pid"}))` and sends the receipt `{"issuedAt","signature"}` in the decision, together with the grants it signed. The phone never sees the decision, so the receipt the relay returned (`GET /v1/pair/{pid}`, `receipt: {issuedAt, signature}`) could not be verified by the phone alone: a client that verifies it, as section 4.10.2 says it must, had no way to learn the grants and failed closed, and the recorded ceremony verified only because its reader took the grants from the desktop's decision request. The relay now stores the sorted grants of the approval in the receipt and returns `receipt: {issuedAt, signature, grants}`: the set that is in the signed document, sorted by code point, no repeats (the approval is refused if it has one). The phone builds the document from exactly the returned grants and verifies; the signature covers them, so a relay that returns other grants fails the verification, and the relay gains no power from the member (it could already return any receipt). A phone refuses a receipt without `grants`, with grants that are not sorted or repeat, or with a name outside the fourteen of section 4.14 (it would otherwise store a grant its decoders do not know). `pairing-fetch-response.schema.json` requires the member (it allows others, as every schema of the package does); a rendezvous that was approved before this change has a receipt without it, lives at most ten minutes after it is read, and a phone that meets one fails closed and pairs again. None of the code of the shipped Aokie plugin and phone reads `GET /v1/pair/{pid}`, `sealedToken` or `receipt`: the phone's pairing code reads the desktop's offer and its own response (the texts the relay stores and returns verbatim, which this does not touch), and the compatibility routes are not affected.
61. **A plain-http relay is outside the schemas, by design.** `Config::normaliseUrl` accepts `http://` for a loopback host only (`127.0.0.1`, `localhost`, `[::1]`), so that the relay runs on a developer's machine and under its own tests, which drive it over `php -S` on loopback; every other `public_url` must be `https://`. `AdmissionApi` builds every URL from `public_url`, so on such a relay the admission's `gatewayUrl` is `ws://127.0.0.1:port/v2/realtime` and the three `relay` URLs are `http://`: the Android emulator test of the shipped phone, which runs its real carrier against a loopback relay, meets exactly that. `admission-plugin-response.schema.json` and `admission-mobile-response.schema.json` require `wss://` and `https://` (what a deployed relay sends), and are not loosened: a schema that admitted http would admit a relay that sends a bearer in the clear. The recorded fixtures and the conformance suite therefore use an https `public_url`; the relay's own tests, which need http on loopback, would break if the relay refused it, so there is no code change. A client may use an http loopback relay in a test build and must not treat what it gets as conforming.

## Design defects found while building RL-06 and RL-07

Where the design (or the first version of this package) is wrong or leaves a hazard, and what was done. None changed the code beyond what the interpretations say.

1. **The challenge's 25 s life gives a phone clock only five seconds of slack behind the relay.** `EndpointChallengeFrame::validate` refuses `expiresAt - now > 30` and `expiresAt <= now`. With 25 s a phone whose clock runs 6 s behind the relay's is refused, while one 24 s ahead is accepted. FormLogic's 25 has the same shape. A life of 15 s would tolerate 15 s either way (a phone clock 15 s behind sees 30 s ahead, one 14 s ahead sees 1 s). Kept at 25 as the default (the design fixes it), and made a config value, `call.challenge_s` (10 to 30, default 25), so that the owner can choose without a change to the code; whether the default should be 15 is the owner's to decide.
2. **A 503 from the stream or 403/404 from any route makes the plugin re-bootstrap.** `relay_status_error` (both carriers) reads 503 as "unavailable for this app" and ignores `Retry-After`; the plugin absorbs only three stream failures with a one second pause before it fails the session, so about four seconds of hard-limit refusals (`503 companion_unavailable`, section 10.6) drop the whole Companion surface. The design and FormLogic both say 503, so it is kept; a 429 with `Retry-After` would be absorbed.
3. **The TURN username.** The README and Appendix A5 name `<expiry>:<subjectId>`, FormLogic uses an opaque keyed hash (interpretation 36).
4. **The first schemas were stricter or looser than the decoders**: `expiresIn` at least 31 (the decoder's margin is 10; a phone accepts 1), no `username` and `credential` on a STUN entry (the plugin requires both), no `time` and no strictness on the frames answers, a `retryAfter` in the compat error.
5. **A phone paired to a personal relay has no signed discovery document**, and its admission check compares `gatewayUrl` and `relayOnly` with values from one, and `appId`/`subjectId` with its session. Where the phone gets them for a relay is a phone-side decision the relay cannot make; the fixtures README lists what the Rust contract test needs.
6. **The shipped carriers never send `relay-poll`** (the design's poll-mode transport) and ignore `relay.mode`; only a future carrier would use it.
7. **Aokie's own `aokie-companion-realtime.v2.schema.json` requires `approvedPeerKeyThumbprints` on a mobile challenge** while its decoder defaults it and refuses a non-empty one; the relay follows the decoder and FormLogic.
8. **FormLogic's own stream has the same latent bug.** It writes frames with `JSON_UNESCAPED_UNICODE` to the same carriers, which decode each network chunk on its own (`companion_relay.rs`); a chunk boundary inside a character corrupts it there too, only rarely seen because a call's frames are mostly ASCII. The relay avoids it (Interpretation 52) and FormLogic should escape non-ASCII in its SSE frames as well.
9. **The relay's limits are tighter than the decoders'.** `limits.rosterMax` is 16 phones and an `appId` is at most 64 characters (design 4.2 and 4.10.6); the shipped decoders accept 64 roster entries and an app id of 200 characters. A plugin or a phone at the decoders' limits (a seventeenth phone, a hundred-character app id) meets a refusal it would not meet with FormLogic. The limits are the design's and are kept; `rosterMax` can be lowered in the config and never raised past 16.
10. **"The shipped plugin and phone need no change" is not true today.** They signal through the relay unchanged only on a host that passed the stream probe (otherwise an admission is `422`: Interpretation 40, and both ignore `relay.mode`), only with the phone's clock inside the challenge's margin (defect 1), and only because of workarounds in the relay: a post to a gone phone is a success (Interpretation 46), a display name is cut to 120 bytes (47), an absent `supportedTransports` is `["relay"]` (40), frames are sent in ASCII (52). What still needs a change in the clients: (a) `relay_status_error` treats a 403, 404 or 503 from any route as a reason to re-bootstrap the whole carrier, so a `503 companion_unavailable` at the hard limit still drops the session (defect 2); (b) both carriers ignore `Retry-After`, so the relay's `429` and `503` answers are retried at the carrier's own pace; (c) the phone has no way to discover a personal relay's gateway, app id and subject id, and no OAuth route to it (defect 5); (d) the desktop broker sends no `supportedTransports` and the carriers never send `relay-poll` (defect 6), so a host that cannot flush has no call signalling for them; (e) the challenge's margin (defect 1), for which the relay has `call.challenge_s`; (f) FormLogic's own stream should escape non-ASCII as well (defect 8).
